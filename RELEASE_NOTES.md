## Unreleased

### Highlights

**Approve a changed tool from a client.** `GET /v1/tools/{set}/diff` shows a set's live tool definitions and their pins, and `POST /v1/tools/approve` approves tools at the pins the client showed, writing the pins as `aimux tools approve` does; a pin that no longer matches the live definition is refused (`409 pin_stale`), and a tool whose source address or hidden request details changed is left to the Mac (`409 review_on_mac`). `aimux tools approve` and the API now write the pins under one lock, so neither drops the other's approval. The source is listed afresh before the pins are checked, and the pins are checked against what that relist saw, under the approval's tool configuration (the gateway applies it first, so back-to-back approvals work) (a source too slow for the 5-second budget, such as one with many pages of tools, answers 503: try again), and each approval's audit line names the set, the tools and their pins. It needs `tools_approve: true` for the client in `clients.yaml` (off by default; the file `aimux setup` writes lists it for Wingman) and a fresh step-up from one of the client's `step_up_kinds` on every request, so for now only a device client can approve. See the remote access guide.

**New tools on a server show up, and join a set in one step.** `aimux tools status` lists a tool a source offers that no set lists and no pin covers as `new_on_server` (`GET /v1/tools` reports them on the set as `newOnServer`); nothing grants it. `aimux tools approve <source>/<tool> --add-to-set <set>` prints its definition, adds it to the set in `tool-sources.yaml` (comments kept) and pins it, warning when the tool does not declare `readOnlyHint`. A sandbox turn whose profile has tools held for review now says so first, in one `aimux_notice` session update ("2 tools held for review (...): run aimux tools status"), and the Wingman host relays it as a `notice` event; the host also passes the API's error `code` (such as `image_invalid`) on error events.

**The sandbox tool gateway runs on its own.** The read-only tool gateway that OpenShell sandboxes reach on `host.containers.internal:7390` is now a worker of the `aimux mcp proxy` service (`aimux mcp proxy gateway serve`), with its own pool of backends, instead of living inside `aimux remote serve`. Each sandbox turn's token is a lease (15 minutes, renewed every 2 minutes while the turn runs and put again soon after a restarted worker answers (status checked every 10 seconds, every second while it does not answer); for 15 seconds after it starts, the worker holds calls with a token it does not know yet instead of answering 401 (at most 64; more get 503), deleted when it ends) that `remote serve` puts on the worker over `~/.aimux/gateway.sock` (mode 0600, only your user). A new lease first lists its servers afresh, so a tool a backend changed since the last listing is not served to that turn; when a backend is slow the listing stops waiting after 5 seconds and the lease is accepted anyway (each call is still checked against its pin). Run `aimux mcp proxy gateway install` once: it runs the worker under launchd (`com.aimux.tool-gateway`); without it, a Workspace turn fails at once with that command in the error. `aimux mcp proxy gateway status`, the `tool gateway` line of `aimux mcp proxy status` and doctor's `gateway.worker` check show whether it runs. `aimux sandbox verify` uses the running worker, so `remote serve` no longer has to be stopped first.

**The tool gateway logs its retries of a down backend.** A backend that was down when the gateway worker started is still retried every minute and served once it answers (`backend <name> now available`); each failed retry is now logged too, at most once every 10 minutes per backend (`backend <name> still unavailable (retried): <reason>`), so the log shows the worker is still trying.

### Fixes

- **Setup, doctor and sandbox status cover the tool runner.** `aimux doctor` checks the `aimux-tools` runner image (`sandbox.runner_image`), its `aimux-github` provider when an approved source needs it (`sandbox.runner_provider`) and warns about sources left out of the runner (`sandbox.runner_sources`); `aimux setup` builds a missing runner image and creates a needed runner provider, and its summary counts both; `aimux sandbox status` shows the runner image and lists each source left out of the runner with its reason (`runner_image`, `runner_dropped` and `runner_provider.needed` in `--json`).
- **Status says how old each state is.** `aimux mcp proxy status` shows a failed server as `failed 12m ago`, and the tool gateway line (also `aimux mcp proxy gateway status` and doctor) says when the worker started and when each down backend was last checked (`down: wiki (checked 40s ago)`), so a last-known state is not mistaken for a live one. The worker's control status has a new `checked` map for this.
- **`aimux mcp proxy status` reads at a glance.** Problems come first: failed servers with their error and stderr, then live servers whose last error is recent (yellow, with its age); then the active ones, and the servers never started on one line instead of a row each (`--all` brings back a row per server). A header gives the pid, version and uptime and a coloured count per state, with an upgrade restart pending in yellow beside the command to run; the hooks, removed entries and servers kept direct are dim notes at the end. An error the server has since recovered from (it answered a call or started well afterwards, in the same session for a per-session server; a call that only came in, was cancelled or finished on a backend a reload retired does not count) no longer shows in red forever: it is left out, and `--all` shows it dim as `(old)`. A removed server's current failure keeps its error and stderr under `--all`. Something else on the port that answers without a running proxy's report (running, a pid, a start time) is an error, not a green page. A reply that races the caller's cancel is not counted as an answer. On a terminal the page fits its width in terminal cells, so wide characters count twice (long errors end in `…`, lists wrap, and a narrow terminal shows names and states only); a proxy that gives no status (HTTP error, timeout) still gets the install warnings printed before the error, without waiting on the tool gateway, and a gateway that stalls never holds back the proxy's part of the page (text only; `--json` just fails); piped, with `NO_COLOR` or `TERM=dumb` it is plain text. `--json` keeps its shape and adds, per server, `lastOK` (when it last answered a call; left out until it has) and `errorPast` (whether its last error is past, as above; given whenever there is a last error, so a proxy from before this release that sends none is told apart: the page then takes its errors as old unless one came after the server's last answer), and its `install.keptDirect` names each server once. A probe that fails on a server that keeps running is counted as `probe failed`, not `failed`. The tool gateway line uses the same style (`tool gateway ● running 17h · 0 leases · 5 backends`, a down backend in red), also in `aimux mcp proxy gateway status`. A server kept direct no longer appears twice (`brand, brand`) when the last install recorded it as needing OAuth and its entry has since gained an `oauth` key.
- **Failures carry a code and a message for a person.** A profile session's start or turn that fails because the tool gateway is not running (`tool_gateway_not_running`), the gateway worker did not take the turn's lease (`gateway_backend_down`), the profile does not compile (`profile_unavailable`) or the OpenShell gateway is unreachable (`sandbox_gateway_down`) answers with that code and a message saying what to do, in the error body and in the `turn_error` event (now `{"error","message","code"}`); the Wingman host forwards both on its `error` events. The event's `error` is that message too; the cause, which can name sandboxes, hosts and command output, goes only to the `remote serve` log. `sandbox_gateway_down` is set only when `openshell -g local status` fails too. See **Coded failures** in the remote access guide.
- **A server the gateway serves nothing from is left out of the turn.** When every tool a profile grants on a server is held for review, a sandbox turn's MCP config no longer lists that server, so the agent does not try a server that answers with no tools; the turn's notice names it (`slack: 5 tools changed, held for review, left out of this turn`).
- **Installing from a new binary switches the launchd job to it.** `aimux mcp proxy install` run from another aimux binary than the one the `com.aimux.mcp-proxy` job runs now rewrites the plist's program to this binary and restarts the job (before, a running proxy only reloaded and kept the old binary). `aimux mcp proxy gateway install` does the same for `com.aimux.tool-gateway` and waits for launchd to unload the old job before loading the new one. Both name the binary the job ran before, and both put the old plist back and load it again when the new binary's daemon does not answer. Installing from an aimux built inside a git worktree (other than the main clone), on `PATH` or not, warns and needs `--allow-worktree-binary`, since the job would break when the worktree is removed. `gateway install` counts only the launchd job's own worker as ready, and it and `gateway uninstall` take one lock.

## aimux v0.15.0

### Highlights

**Profiles.** A profile is a named contract for what an agent session may reach (tools, network, files, credentials, settings) and where it runs. Builtins ship with aimux, yours are YAML files in `~/.config/aimux/profiles`, a child may only narrow its parent, and every resolved profile has a digest. `aimux profile list|show|check|migrate` manage them, and the [Profiles guide](https://aimux.ai/guides/profiles/) has the format.

**One API for local clients.** The remote API now serves programs on your Mac over Unix sockets, with a scope per client in `~/.config/aimux/clients.yaml`: which profiles it may ask for, how many sessions and turns it may run, and which routes it can reach. Every request of a local client is audited.

**A reading side panel with safe lookups in your own tools.** Wingman is a Chrome extension (in the [wingman repo](https://github.com/zanetworker/wingman)) that summarizes the page you are on and answers questions about it. It is a client of that API with three modes: Page runs under the `page` profile; Web searches and reads the public web, read only, under the `research` profile (the page's text goes along only when "Use this page" is on, which starts off on Gmail, Google Docs, Drive and Calendar, Slack and Atlassian pages); Workspace also searches your research wiki, Jira, Slack, Gmail and Drive, read only, under the `work-readonly` profile. `aimux browser` is its back end.

**Auto picks the mode.** `POST /v1/route` chooses Page, Web or Workspace for a question, among the modes the client may use; only the question and three yes/no facts go to OpenRouter (`cloudflare/clef-flash`, requested with zero data retention), the key comes from the Keychain item `aimux-openrouter` (or the 0600 file `~/.config/aimux/keys/openrouter`), and when it is unsure, has no key or is slow, Wingman asks you instead, saying when the key is missing. A question that tells the router which mode to pick is never sent to the model; you pick. It also decides Page without asking when the page is readable and attached ("Use this page" on) and the model puts Page first at 50% or more of its own probability (read before the allowed modes are renormalized), even below the confidence bar; the log line says `"rule": "page_attached"` and carries `raw_probabilities`. Picks and whether you kept or changed them are logged in `~/.aimux/logs/decisions.jsonl` (rotated at 10 MB) without the question text. `remote serve` reads the key and opens the connection to OpenRouter as it starts, and the key read does not count against the 5-second decision budget (OpenRouter usually answers in under a second but sometimes takes several), so the first question after a start is not lost to a cold Keychain; an OpenRouter request not answered after 1.2 seconds gets an identical second one and the first answer wins (`hedge` in `deciders.yaml`; each request is billed, `chat` backends are never hedged, and the decision log says `hedged` when a second went out); after 1.5 seconds Wingman offers Pick now; each undecided route is a line in the serve log with the key and request times. A `chat` fallback in `~/.config/aimux/deciders.yaml` (through Anthropic) is supported.

**Earlier questions follow a mode change.** `POST /v1/sessions` takes `prior`, up to 5 earlier questions of the page's conversation (2,000 characters each, questions only, no answers or page text), so the new mode knows what you asked before; the prompt frames them as untrusted data before the question. aimux picks them itself when a request has no `prior`: when the page's last answered question ran in another mode, it sends that page's last 5 distinct questions (same client, browser profile and URL), so every client gets the same carry-over; an explicit `prior`, even `[]`, overrides it.

**Ask about a screenshot.** `POST /v1/sessions` takes `image` (PNG, JPEG, WebP or GIF, at most 1.5 MiB of base64, one per question; anything else is `400 image_invalid`), and Wingman sends the image you paste or drop into the question box. Page sends it to its Claude session as an image block; Web and Workspace start Claude Code with `--input-format stream-json` and one user message holding the prompt and the image (a question without an image runs exactly as before). The prompt frames the image as untrusted data from your screen, like page text, and it never goes to the mode router. History marks a question asked with an image (`"image": true` on the turn in `GET /v1/sessions/{id}` and Wingman's history), without keeping the image. With a profile the request body may now be up to 6 MiB (was 4 MiB).

### Upgrading

Every `aimux remote serve` now does the following, whether or not you use Wingman:

- creates `~/.aimux/wingman/sessions`,
- listens on the Wingman socket, `~/.aimux/clients/wingman.sock`, unless `clients.yaml` removes it,
- refuses to start when the socket's folder (`~/.aimux/clients`) is open to group or others,
- opens the audit log, `~/.aimux/logs/remote-audit.log`, and stops if it cannot, and
- refuses to start the tailnet listener when `remote_access.device_login` is `false`, unless you pass `--unsafe-no-device-login` (any local process could claim an allowed tailnet login). `--local-only` needs no device login.

Also:

- **The work sandbox is `aimux-work-readonly`.** `aimux remote serve` creates it from the compiled `work-readonly` profile on the first work question and keeps its policy (with its digest) in `~/.aimux/sandboxes/`. The `wingman-work` sandbox earlier builds made is no longer used and can be deleted with `openshell -g local sandbox delete wingman-work`. `aimux browser setup` no longer creates or recreates a sandbox.
- **Approvals take effect on the next turn.** `remote serve` rereads `tool-sources.yaml` and the pins on the next work question after either changes (and once a minute regardless); that turn compiles against one snapshot of both (its version is logged) and the gateway applies it before the turn's token is used, refusing what it has not applied yet; the gateway also retries down backends at most once a minute; no restart needed. A backend that stays up and changes a tool is noticed at the next call to it (its pin check lists it) or the next once-a-minute relisting, which runs in the background and never holds up a turn: the tool stops being listed to the sandbox and `GET /v1/tools` says `changed`. A relist that fails marks only that source `unknown (relist failed)`; it is still served under its pin check. A session granted under an older snapshot loses only the tools whose pins changed since. A registry edit restarts only the backends whose URL or folder changed, after their calls in flight; `cli` and `http-openapi` backends restart on every new snapshot, pin changes included, since the runner's policy follows the pins. A pins file that does not parse fails closed (nothing granted or served) until it is fixed. A backend left with no pinned tool stops serving at once, even to sessions already open. A backend that was down at setup only leaves out its own tools; `work-readonly` still answers from the others.
- **A tool change a backend announces is acted on at once.** When a tool backend sends `notifications/tools/list_changed`, the gateway lists it again right away: a call to a tool that changed is refused and the tool stops being listed to the sandbox. A backend that does not announce changes is still caught within a minute (the next pin check after its listing expires, or the once-a-minute relist). To hear these, the gateway keeps a GET stream open to each HTTP tool backend; if that stream keeps failing, the first failure is logged once and, after 5 failures in a row, the backend stops listening and falls back to the minute rule.
- **Two new tool source types.** `tool-sources.yaml` sources can be `cli` (`pack: gh`, a built-in pack) or `http-openapi` (`spec`, `base_url`, optional `credential`); a source with a key from another type is dropped with a message, and a pack that does not exist names itself (`unknown pack nope`).
- **CLI tools run in their own sandbox.** `cli` and `http-openapi` sources run in one sandbox, `aimux-tools` (image `localhost/aimux-tools:2.103.3`, the sandbox image plus a pinned `gh`). `cli` sources (the `gh` pack) run there now: the gateway and `aimux tools approve` create or update `aimux-tools` on first use (status, diff and doctor only read it) and run each call as validated argv with `openshell sandbox exec`, 30 seconds at most, output cut at 256 KiB, and a network policy refusal reported with its method and path. A `gh` upgrade changes the tools' pins, so they need approving again. `http-openapi` sources run there too (next item). A source whose provider is missing on the gateway is left out with an error naming its Keychain item and `aimux sandbox setup`. `aimux tools approve` ensures `aimux-tools` again after it writes the pins, so the first approve of a `cli` or `http-openapi` set leaves the runner with that set's endpoints and providers. The compiled policy opens only approved sources' read-only endpoints (`gh`: `api.github.com` REST read-only and GraphQL queries) to their binary. Checked live on OpenShell 0.1.7 with the `gh` pack: the GitHub token never appears in the sandbox (its environment has none; the proxy adds the header to `/usr/bin/gh`'s requests only), a `POST` and a GraphQL mutation are refused with `policy_denied`, a binary the policy does not list cannot connect, and `curl` cannot reach `api.github.com`. `aimux sandbox setup` builds the image and, when the secret store (Keychain on macOS, Secret Service on Linux) has the item `aimux-github`, imports aimux's trimmed provider profile `aimux-github` (not OpenShell's built-in `github`, which also opens git transport) and creates provider `aimux-github`; otherwise it says how to add the token. `aimux sandbox status` lists the runner as `(tool runner)` (`runner` in `--json`), and a second `Provider:` line for `aimux-github` (`runner_provider` in `--json`), `missing` when the gateway lacks it; it asks for `aimux sandbox setup` only when an approved source needs it. Status now compiles the runner against the gateway's provider list (it used to search the sandbox list, so a runner set up before its pins were written could show `current`).
- **`aimux tools add cli <pack>` and `aimux tools add http --name <name> --spec <file> --base-url https://...`** add `cli` and `http-openapi` sources and their set `<name>:readonly` without editing YAML (`--tools` narrows the set, `--authorship` as for `mcp`, default `outside`). `http` prints how many `GET` operations it found and how many others it ignored, and refuses a relative spec, a non-`https` base URL, a base host that is an IP literal, `localhost`, an `.internal` or `.local` name or the model host, a host a credentialed built-in pack uses (`api.github.com`: add `gh` with `aimux tools add cli gh`), and `--credential` (credentialed HTTP sources are not supported yet). Both print the next steps: approve the set, then `aimux sandbox setup` if the runner image or a provider is missing.
- **HTTP sources serve OpenAPI GET operations.** An `http-openapi` source serves every `get` with an `operationId` in its OpenAPI file (3.0 or 3.1, YAML or JSON, up to 5 MiB) as the read-only tool `<source>_<operationId>`; other methods are skipped. Its pins cover the method, path template, base URL and parameters, not the description (a spec edit can change description text without approval). Specs over 500 GET operations are refused, and paths whose literal segments are not plain characters are skipped. A call checks its arguments (one escaped segment per path value, no `/`, `\` or `%` in it, no unknown keys, types and enums enforced), is refused when its operation changed since the last listing, and runs one `/usr/bin/curl -q` GET in `aimux-tools` (no `.curlrc` is read); the runner's policy allows `GET` only on the path templates of approved operations. A live `http-openapi` call has not been run yet: this path is tested against a fake runner only. A missing spec, or a base URL the runner refuses (as `aimux tools add http` does), is that source's error only; the other sources keep running. Sources with a `credential` serve nothing yet.
- **Each tool source has an authorship class.** `tool-sources.yaml` sources take `authorship: self | internal | outside` (default `outside`: content anyone outside can write). `aimux tools add` takes `--authorship` (notes default `self`, mcp default `outside`), `aimux tools status` shows a CLASS column (and `authorship` in `--json`), and `GET /v1/tools` returns `authorship` on each set. A notes source migrated from `readonly.json` is `self`. Rollback: an older aimux refuses a `tool-sources.yaml` with `authorship:`; remove the key to go back.
- **Local-only vs full serve.** Opening a Wingman panel starts `aimux remote serve --local-only` when nothing answers on its socket; it now exits after 30 minutes idle. While it runs, a full `aimux remote serve` exits 1 and names its pid: `kill <pid>`, then start the full serve (Wingman uses it too). Two serves of the same kind still print `already running (pid N)` and exit 0.
- **Wingman's broker is gone.** An earlier build ran a broker daemon that held `127.0.0.1:7390` while a panel was open and for about 30 seconds after the last one closed. One still running after the upgrade keeps the port until then: close the panels and wait before the first work question or `aimux browser verify`.
- **`aimux sandbox verify` cannot run while `remote serve` holds `127.0.0.1:7390`**, which it does after its first work question. Stop `remote serve`, run `verify`, start it again.
- **Pins are reviewed, not taken on trust.** Only `aimux tools approve <set|set/tool>... | --all` writes `~/.aimux/tools/pins.json` (now version 2: hash, the reviewed definition, `approved_at` and source; a version 1 file is read and upgraded on the next approve). `aimux tools status` shows each tool as active, unpinned, changed, unavailable, source_changed (approved from another URL or folder than the registry now names; approve re-stamps it) or not_in_registry, and `aimux tools diff` shows field by field what approving would change. `aimux browser setup` no longer pins anything: it prints the tools that need review and the commands to run (`--accept-pins` approves all of them for automation, with a warning). A pin detects schema changes; it does not prove a tool is read-only. `aimux tools approve` prints each definition it pinned with its short hash, `aimux tools diff` prints the live hash, and `approve <set/tool> --expect <hash>` refuses when the definition changed since you looked. `aimux tools add notes --folder <dir>` and `aimux tools add mcp --name <n> --url <loopback url> --tools a,b` add a source and its `<name>:readonly` set (approving nothing), and `aimux tools remove <source>` takes one out (its pins are kept, unused).
- **Upgrade path for tools.** Nothing needs approving again. The first `aimux setup` (or `aimux browser setup`, or the first `aimux remote serve` start, which logs one line) migrates `~/.aimux/wingman/readonly.json` to `~/.config/aimux/tool-sources.yaml` and renames it `readonly.json.migrated`; the wiki stays the source `wiki`, so its pins, tokens and tool names stay valid. A version 1 `pins.json` stays valid as it is; the first `aimux tools approve` rewrites it as version 2 and keeps the old file as `~/.aimux/tools/pins.json.v1-backup`. Then run `aimux tools status` to see what, if anything, needs review.
- **Rolling back.** Builds before this one read neither `tool-sources.yaml` nor a version 2 `pins.json`. To go back: stop `remote serve`, rename `readonly.json.migrated` back to `~/.aimux/wingman/readonly.json`, and copy `pins.json.v1-backup` over `pins.json`. The backup holds the pins as of the upgrade, so every approval made after it is lost on rollback, backup or not: approve those tools again with the older build.
- **v1 profiles.** `aimux profile save|get|delete` still work on `~/.aimux/profiles.json` and print a note. Run `aimux profile migrate` to write them as v2 files; it never overwrites a file. A v1 `mode` is not carried (v2 has no mode field yet); migrate prints a warning for each profile that had one.
- **`remote_access.step_up_legacy`** (default `false`) also asks for a fresh Secure Enclave login for new sessions started without a profile.
- **`aimux setup` and `aimux doctor`.** `aimux setup [--extension-id <id>]` checks the sandbox, tools, router, browser and gateway and runs only the missing steps (asking on a terminal, `--yes` to run them without asking, none when there is no terminal and no `--yes`); it offers changed tools for review on a terminal and never approves otherwise. `aimux doctor` runs the same checks read-only (it writes nothing) with one fix per problem and exits 1 on any failure (warnings alone exit 0). `aimux browser uninstall` removes the Chrome host. See [Troubleshooting](https://aimux.ai/guides/troubleshooting/).
- To try Wingman: load the extension, then run `aimux browser install --extension-id <id>`. For Workspace and Web, store a token with `claude setup-token` and `security add-generic-password -U -a "$USER" -s wingman-claude-oauth -w`, then run `aimux setup` and `aimux sandbox verify`. The [Wingman guide](https://aimux.ai/guides/wingman/) has the steps.
- `aimux browser setup` reads sandbox files from the wingman repo (`--sandbox-dir`).
- **Default remote sandbox image.** A remote launch with no image (none in the launch, `remote.image` empty) now uses `localhost/wingman-sandbox:2.1.319` instead of the OpenShell community base. `aimux browser setup` builds it; to keep the community base, set `remote.image` in `~/.aimux/config.yaml`.
- macOS with Chrome or Chrome Beta only.

### Profiles

- **Format.** `name`, `extends`, `harness`, `model`, `runs` (`host`, `acp`, `sandbox`, `run`), `tools`, `network`, `files`, `credentials`, `settings` and `roles`. Files are read from `$AIMUX_PROFILE_DIR` or `~/.config/aimux/profiles`; unknown fields, a name that differs from the file name and a name that shadows a builtin are errors.
- **Builtins:** `page`, `work-readonly`, `research`, `coding` and `base`. `work-readonly` also asks for `gh:readonly`, used once you add and approve the `gh` source (`aimux tools add cli gh`); until then it is left out and `aimux doctor` does not report it. `research` runs in a sandbox with no tools and network `deny`, allowing `model` and `web`. `research-with-work` is listed but unavailable (`409 profile_not_available`) until a later release.
- **Narrow-only inheritance.** A child may drop tools, network, files and credentials, never add them, and may not switch `network.default` from `deny` to `allow`, inherit your settings or change the harness. `runs` may only move toward more isolation. User profiles must declare `extends`.
- **Commands.** `aimux profile list`, `show <name>`, `check <name>` (exit 1 and the field that widens) and `migrate`, all with `--json`.
- **Enforced and cooperative.** The OpenShell policy (egress, MCP methods and tool names, files) and the tool gateway are enforced outside the agent; the harness config only mirrors them.

### Wingman

- **`aimux browser install --extension-id <id>`** installs the pinned ACP adapter under `~/.aimux/wingman/adapter`, writes `~/.aimux/wingman/host.sh`, pins your extension id in `~/.aimux/wingman/extension-id`, and registers the native messaging host `com.zanetworker.wingman` for Chrome and Chrome Beta, allowing only your extension id. It refuses a temporary `aimux` build unless `--allow-temp-binary` is set.
- **`aimux browser host`** is the native messaging host Chrome starts for each open panel. It checks that Chrome's caller is the pinned extension, then only relays the panel's requests to the remote API on the Wingman socket, and starts `aimux remote serve --local-only` when nothing answers there. Closing a panel ends only its own host. Its log, `~/Library/Logs/aimux/wingman/host.log`, notes only that the host started, refused a caller or started `remote serve`; the per-request record is the audit log.
- **`aimux browser setup`** makes sure the tool-source registry `~/.config/aimux/tool-sources.yaml` exists (sources and reviewed tool sets; migrated once from `~/.aimux/wingman/readonly.json`, kept as `readonly.json.migrated`, or the defaults, which have no notes folder), reports the tools that need review (`aimux tools approve` pins them), writes `clients.yaml` if missing, builds the sandbox image, and creates the `wingman-claude` provider from the Keychain item `wingman-claude-oauth`. It creates no sandbox: `aimux remote serve` creates `aimux-work-readonly` from the compiled `work-readonly` profile on the first work question.
- **`aimux sandbox status|setup|verify`.** `status` (read-only, `--json`) shows the sandbox image, the `wingman-claude` provider, the OpenShell gateway and, per sandboxed profile, whether its sandbox runs the policy compiled now (`current`, `stale (applies on next turn)`, `missing (created on first use)`); `setup` builds the image and creates the provider when missing and creates no sandbox; `verify` is the old `aimux browser verify`, which still works and prints a note that it moved. `aimux browser setup` runs the same sandbox steps and points at `aimux sandbox status`. `aimux browser status` shows the Chrome native host registration, the pinned extension id and the host wrapper.
- **`aimux sandbox verify`** (formerly `aimux browser verify`) compiles `work-readonly`, makes sure `aimux-work-readonly` exists with that policy, and checks from inside it, with `node`, that the internet and the host's `:7381` proxy (on loopback and through the host gateway) are blocked, and that the read-only server accepts an issued session token and rejects a request without one. It stops clearly when the OpenShell gateway is down.
- **Three modes.** Page questions run in an aimux ACP session with no tools, no MCP servers and no user settings (Sonnet by default, Opus from the panel's picker). Web questions run `claude -p` in the `aimux-research` sandbox with only WebSearch and WebFetch; each fetched URL shows under the answer. Workspace questions run `claude -p` in the `aimux-work-readonly` sandbox against the read-only server only. The mode control (Page, Web, Workspace), not the model or the page, picks the lane, and it goes back to Page on another page or tab.
- **Use this page.** Web mode has a "Use this page" chip that decides whether the page's text goes along; it starts off on private sites (non-web URLs, IP and local hosts, Google Workspace, Slack, Atlassian, Red Hat internal hosts, Outlook, SharePoint, Teams, Zoom, and any site marked "Always treat this site as private"), where Web then sends no title and the sandbox sees only the URL's origin, not its path (the conversation is still kept per page). Turning it on or off starts a separate conversation, so text sent with it on never reaches a question asked with it off. Page and Workspace conversations from before this release start fresh once: their next question opens a new session, and the earlier turns stay in history.
- **History.** The panel's history comes from Wingman's sessions in the remote API (`GET /v1/sessions?client=wingman`); deleting a page hides its sessions. A page is its URL without a plain `#anchor`; a fragment with a `/` (each Gmail email, each route of a hash-routed app) is its own page with its own conversation. The old `~/.aimux/wingman/history.db` is no longer used. Each browser profile (Chrome, Chrome Beta, each Chrome profile) keeps its own conversations: the extension sends a per-profile `instance` and the server keys page sessions on it; sessions from before keep showing in every browser. Session search and the session MCP tools skip the page-lane session files.

### Remote API

- **Local client sockets.** `aimux remote serve` listens on a Unix socket for each client in `~/.config/aimux/clients.yaml` with a `socket` (Wingman: `~/.aimux/clients/wingman.sock`, folder `0700`, socket `0600`). The socket names the client: no tailnet or device login, and the client is held to its own profile sessions, scope and limits, each request audited (client, action, profile, digest, page host and result; never text, pages or tokens).
- **Client scopes.** Defaults for `wingman` (four profiles, 2 sessions running, 20 turns a minute), `device` (those and `coding`, step-up for a Secure Enclave device) and `cli` (every profile). Wingman can never use a profile that runs on the Mac.
- **`--local-only`** serves only those sockets, with no `--allow` and no device login, and exits on its own after 30 minutes with no local request and no running profile session. A second `remote serve` of the same kind prints `already running (pid N)` and exits 0; a full serve that finds a local-only one exits 1 and names its pid (`kill <pid>`). `GET /v1/health` has `localOnly`.
- **Profile routes.** `GET /v1/profiles` and `GET /v1/profiles/{name}` (capability `profiles`); `POST /v1/sessions` takes `profile`, `url`, `title`, `pageText` (up to 512 KiB), `originOnly` (the sandbox prompt names only the URL's origin) and `model` (`sonnet` or `opus`), and `POST /v1/sessions/{id}/messages` takes `model`. `GET /v1/sessions` takes `client` and `url`. `PATCH /v1/sessions/{id}/meta` takes `hidden`. `GET /v1/health` has `profileStore` while the profile sessions file cannot be read.
- **Which tools a profile gets.** `GET /v1/tools` lists the tool sets the profiles in the caller's scope request (Wingman: those of `work-readonly`), each `available`, `partial` or `unavailable` with a reason, and each tool `active`, `unpinned`, `changed`, `unavailable`, `source_changed` or `unknown` (the tool gateway has not listed its source yet) with its `approvedAt`. Read-only: it reads the snapshot the next turn uses and what the gateway already listed, and contacts no backend. Sets the compiler would leave out are listed with why; a pins or registry file that does not load is one error and every set unavailable. No definition, token, backend error, file path or non-loopback URL is returned. Confined clients may call it; servers that offer it list the `tools` capability. `remote serve` migrates `readonly.json` once when it starts; its reloads (turns and this route) only read.
- **Host and run profiles** (`coding`, `base`, `research-with-work`) are listed `available: false` and refused with `409 profile_not_available` until they have an engine; start a host session without a profile. An engine failure answers `500 internal` with no internal detail.
- **New error codes:** `unknown_profile`, `profile_not_allowed`, `step_up_required`, `profile_not_available`, `page_too_large`, `client_limit` (with `Retry-After`), `forbidden_for_client` and `not_found`.
- **Local clients are confined.** They reach health, the contract, the profiles, the tool sets (`GET /v1/tools`), their own session list, new sessions and, for the sessions they started, the detail, events, messages, cancel and meta; any other route (describe and the queue included) is `403 forbidden_for_client`, and another session is `404 not_found`.
- **Profile sessions run for real.** Page sessions use the Wingman adapter; sandbox sessions run `claude` in the profile's OpenShell sandbox, with the read-only tool gateway on `127.0.0.1:7390` started on first use, and resume after a restart.

### MCP proxy

- **Allowlist profile:** `tools/list` shows only allowlisted `(backend, tool)` pairs; a call to anything else is rejected and logged. Tools a backend gains later stay hidden until allowlisted.
- **HTTP backends:** the proxy can forward to Streamable HTTP MCP servers.
- **HTTP servers move behind the proxy too.** `aimux mcp proxy install` now also moves Claude Code's HTTP servers that need no OAuth (no auth, or a static `headers` map). Header values move into the Keychain item `aimux-mcp-proxy/<server>` and out of `~/.claude.json`, the manifest and the backup install writes; `uninstall` restores each entry byte for byte from it. Servers that need OAuth (`kept direct: needs OAuth (later)`), are down, use SSE or a `headersHelper` stay direct with the reason. `--skip` and `--unskip` accept any server name. A `${VAR}` anywhere in a URL keeps that server direct (the URL is saved as written); query values and userinfo passwords are hidden in errors and logs like header values. If a server's Keychain item is gone, `aimux mcp proxy uninstall --without <server>` removes its proxy entry and restores the rest. The manifest moves to format 3; an older aimux refuses it. Checked live on the owner's Mac: the dry run listed 7 HTTP servers to move and 9 kept direct; a new Claude Code session called deepwiki through the proxy; `uninstall` restored all 7 HTTP entries byte-identical (hash compare) and the 28 stdio ones; a reinstall moved 35 servers with 0 failed.
- **Saved HTTP definitions:** `~/.aimux/mcp-servers.json` keeps HTTP servers under `httpServers` (`type`, `url`, and `secrets`: a Keychain reference per header, item and field), apart from the stdio definitions in `mcpServers`, so an older aimux still reads the file (it sees only stdio servers); a file with HTTP definitions inside `mcpServers` is read too and rewritten on the next save. The proxy resolves the references each time it starts a server, and its errors never carry a header value. The file is generated state with `"schema": 2` and `"generatedBy"`; a newer schema is refused. While the running proxy is another version, `install`, `edit` and `refresh` refuse to touch HTTP definitions and name the binary its launchd job runs, to update or reinstall from. `aimux mcp proxy edit` edits stdio servers only and refuses an HTTP one.
- **Token-guarded listener:** a bearer token is required on every request; each session of the tool gateway gets its own.
- **Wiki tools:** built-in `wiki_search` and `wiki_read` serve Markdown files under a configured root, resolve symlinks, and refuse paths outside the root, non-Markdown files and oversized files.
- **New MCP servers move behind the proxy by themselves.** `aimux mcp proxy install` now adds two Claude Code hooks: after a session runs `claude mcp add` (or `add-json`, `add-from-claude-desktop`), the new stdio server is moved behind the proxy and the session says so (or names the server that failed); when a session starts, one line names any stdio servers still direct, such as ones added in a terminal. A project-only server is explained, not moved. `status` shows whether the hooks are on; `uninstall` removes them. Re-run `aimux mcp proxy install` once to add them to an existing install.

## aimux v0.13.0

### Highlights

**Session search, rebuilt.** `aimux sessions` uses one ranked SQLite index for the CLI, TUI and web dashboard: BM25 keyword search, optional OpenAI-embedding semantic and hybrid ranking, exact "quoted phrase" search, and match snippets. It replaces the ripgrep backend.

**Only your sessions.** Automated sessions (`claude -p`, cron jobs, SDK runs) are hidden in every list by default; `^a` or `--automated` shows them.

**Sessions over MCP.** `aimux mcp serve` exposes session search, transcript reading and resume as MCP tools; remote agents move behind `--agents`.

### Breaking
- Gemini provider removed (#41)

### Session picker
- `^l` / `--live`: only sessions running in a terminal now
- Click a row to jump to its iTerm pane or resume it
- `^y` copies `cd '<path>' && claude --resume '<id>'`
- `^s` cycles keyword and semantic modes; `^/` toggles the preview
- Rows and header size themselves to the terminal; preview sits beside the list at 140+ columns, below it otherwise

### Fixes and speed
- About half the search latency; persistent index refreshes incrementally
- Session archive dir indexed so sessions outlive Claude Code's 30-day cleanup
- Concurrent MCP calls no longer lock SQLite

### Remote agents
- Run agents on OpenShell and Kubernetes backends; the web dashboard can launch, kill and clean up sandboxes like local agents (#40)
- Web and TUI show gateway health, sandbox badges and kill feedback; launch errors appear in the dialog instead of failing silently (#42)

### Sessions and launch
- Sessions view and CLI default to the current directory; `A` (TUI) or `--all` (CLI) shows every project
- `default_mode` config sets the permission mode for spawned and resumed sessions; `Ctrl+b` toggles bypass/default in the live session view

### Under the hood
- Platform refactor: Provider / Environment / Coordination split, SDK mode design (#48)
- Dependency updates (OpenTelemetry, client-go, protobuf, go-redis, mcp-go)
