aimux · the design on one page

One record, one base, one door

The five-minute version. Everything here is expanded in the longer review and the spec.

The problem

Your agents work through several aimux pieces that were each built alone. Each keeps its own notes in its own shape, so you cannot ask one question across them: what did this cost, what did the agent actually do, was it any good, and should the next one go somewhere else.

The idea, in one picture

Who writes a line, when, and where

Each long-running piece writes its own lines into its own file, when an action finishes. The one exception is tool calls reported by a hook, which go through the collector. Reading is the only thing that brings the files together.

  • Writing happens after the action, so nothing waits for it. If a write fails, the action still completes and the miss is counted.
  • Every tool call has exactly one line that counts. Where a hook reports it, that is the record; the MCP proxy's line for the same call is only a cross-check. Nothing is counted twice.
  • The hook cannot own a file, because many hooks run at once, one per tool call. So it passes its event to the collector, which is already running and already has a way to receive it.
  • A refusal is written by the door that refused. There is no separate policy process.
  • Your labels are not in the ledger. They stay where they are today and connect through the conversation and turn tags.

Is that reliable enough?

For counting cost and seeing what happened, yes. It is not a tamper-proof audit log and does not claim to be: a line is written after its action, so a crash in between loses it. What the design adds is a way to know how complete it is, instead of hoping:

  • Every writer numbers its lines. A missing number is a lost line, and any reader can see it.
  • The hook keeps its event if the collector is down, as a small file the collector picks up later.
  • A regular cross-check against two other sources that already exist: the transcripts, and the totals Claude Code reports itself. The difference per conversation is the measured reliability.
  • A refusal is written before the answer goes back, because it is the one line whose loss matters.

Who joins it all up?

Nobody, afterwards. The joining is decided when a line is written, because each line already carries its tags. Reading is just: open the files, sort by time, group by tag. One function does that, and the terminal, the dashboard and the phone all call it. Nothing is guessed from timing; a line with missing tags is shown as unmatched.

The five parts

  1. One record. Every model call, tool call and allow-or-refuse outcome becomes one line, tagged with the conversation, turn and call it belongs to (and, for Wingman, the question). Those tags are what connect everything.
  2. One base. The proxies keep their own protocols and share the plumbing. A new proxy only writes what is special about it.
  3. One door, many engines, the right one per task. Codex is the first engine behind the model proxy; Anthropic comes next if a login test passes. Then you can use a different model for each task in one session without losing context: by hand, by role (your main conversation on one model, helpers on another), and later automatically when the saving is worth it.
  4. One view. aimux status shows every background process in one table, and one command upgrades them together.
  5. Evals from real work. A turn you mark as bad, plus what you said instead, becomes a test case that any model can be run against.

Routing per task, without losing context

Context is never lost by changing model, because Claude Code holds the whole conversation and sends it with every request. What a change costs is warm-up: a model that has not seen the recent turns has to read them first, which on a long session took 36 to 56 seconds. So the design is about paying that rarely.

4. Automaticaimux proposes a switch only when the saving on the task is bigger than the warm-up, and shows you the sum first.Paid only when worth it

A written catalog, and "auto"

  • One catalog says what each model is good at, what it is weak at, its speed and cost, and where each claim comes from. aimux models prints it. It is the same file the router uses, so what you read and what it does cannot drift apart.
  • "Auto" is just another model name. You pick a model as you do today, or pick auto and aimux chooses for that task. Naming a model always wins.
  • Auto decides by rules first (the role, what the task needs, the allowance left, the catalog). When the rules do not settle it, it uses the route function Wingman already has, once per task, with the same privacy limits.
  • The catalog learns from your own work: whether you kept a choice or changed it, your labels, and your own cases replayed on each model. It starts from public benchmarks, marked as such, and aimux never rewrites it without you.

Will auto get in the way, and who decides?

  • You write the rules; the proxy applies them. The router is ordinary code inside the model proxy, reading your catalog file. No model makes the choice. At most, a small model names the kind of work, and your file turns that into a model.
  • Nothing changes unless you pick auto.
  • It never interrupts. It chooses only when a session or a helper starts, or when you send a new request. Never mid-step, never while a tool is running.
  • By default it leaves your main conversation alone and chooses only for helpers and new sessions, which costs nothing. Moving the main conversation is a separate switch, off at first.
  • It tells you what it chose and why, in one line, and naming a model always overrides it.

Level 3 depends on something untested, whether Codex can be handed turns another model produced.
