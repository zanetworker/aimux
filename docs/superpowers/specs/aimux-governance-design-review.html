One record for everything an agent does

Governance, metering, actuators and evals, for one developer's machine.

24 NOVEMBER 2026 · COMPANION TO docs/superpowers/specs/2026-11-23-aimux-governance-metering-and-evals-design.md

Why this exists

On 22 November a Codex session sat at Deliberating… 3m 42s. Each step was taking 36 to 56 seconds, and nothing in aimux could say why. The model proxy kept its records in one file, the MCP proxy kept counters in memory, neither named a session, and the built-in tools that do most of the work crossed nothing at all.

Adding one line of detail to one of those records found the cause in minutes: Claude Code was splitting tool results across messages, so the proxy threw away its cached conversation on nearly every step and reprocessed 280,000 tokens. Two fixes later, fallbacks went from 203 in a day to 2, and the median step went from 36.5 seconds to 4.8.

That is the whole argument. The expensive part was not the bug; it was the day spent not being able to see it.

The ambition is larger than debugging, and it is yours: the proxy should be where you govern access to everything and see your use, and eventually where actuators act on what they see, switching backends as quotas run down. None of that is possible while the record is missing.

The whole machine

aimux is one Go binary that plays several roles at once. Read the picture top to bottom: ways in, the shared logic, the places every agent action crosses, where agents run, how their work is seen and judged, and what is remembered afterwards.

ways in
Five doors to the same work. The phone goes through the remote API with a device login; other agents reach aimux as an MCP server, which is how a session can search your past sessions.
controller
One Go package (internal/controller, about 5,000 lines) holding every operation you can perform on an agent or a session, each written once as a plain function with its own tests. It builds the list of agents you see (filter, sort, hide, archive, badges, which one needs you next), starts and stops them (launch locally or in a sandbox, resume, kill, jump to a running one), keeps what you say about a session (star, tags, note, value), adds up cost per project, decides when to notify you, and exports a reviewed trace as JSONL or OTLP. The terminal UI, the dashboard, the CLI and the phone call these functions and only draw the result, so a feature added once behaves the same through every door. It is not a process and it does not sit in the path of a request: the chokepoints below run on their own, and today their numbers (proxy health, request stats) are reachable from the CLI only, not through the controller. Moving them behind it is part of the design.
chokepoints
Four places an agent's actions pass through. Three are long-running processes with ports; the fourth is Claude Code's hook mechanism. The next sections are about these.
run
aimux does not replace Claude Code or Codex. It starts them, attaches to them, or continues them, on your machine, in an OpenShell sandbox, or on a cluster.
see and judge
Telemetry arrives as OTLP, is turned into a turn-by-turn trace you can review like a pull request, priced, and labelled. Labelled turns leave as exports. This half is mature.
remember
aimux reads the session files Claude Code and Codex already write, read-only, and keeps a search index over them. It never owns your transcripts.

One request, end to end

The layers make more sense with something moving through them. Here is what happens when you are in a claude-codex shell and ask for a small fix. Claude Code is the harness: it owns the conversation and runs every tool. Codex only decides what to do next.

Three things in that picture carry most of what happened this week. Steps 3 and 8 are prompt caching: when the proxy recognises the conversation, a step costs about five seconds; when it does not, the whole history is sent again, which on a long session took 36 to 56. Step 6 is the blind spot: the tool runs inside Claude Code, under its permissions and your hooks, and aimux only counts it afterwards, as a total per tool, with no record of the single call. And the gold note is the only durable record of the whole exchange: one line, with no prompt and no answer in it.

Where things live

Four background processes, kept running by launchd, and a handful of files. Knowing these is most of knowing the system.

ProcessPortWhat it is for
model proxy7385Codex mode. Changes only through the promote script, which tests a candidate before swapping it in.
MCP proxy7381Starts each MCP server once and shares it across sessions, instead of once per session.
tool gateway7390Serves sandboxed agents a pinned, read-only subset of tools.
collector4318Receives telemetry from Claude Code and Codex and keeps the per-tool token counts.

Is this well structured?

The split is right; the housekeeping is not. Separate processes mean a restart of one does not drop the others' connections, each can change at its own pace, and launchd does the supervising. But nothing treats the four as one system, and it shows:

  • Three builds ran at once when I looked. The program files have since caught up with each other, but the processes already running have not all been restarted. The model proxy was on build 169, the MCP proxy on 128, the tool gateway on 137 from a second copy of the program, and the command line is 178. Only the model proxy has a tested promote step.
  • Two status formats, no overall one. The model proxy and the MCP proxy each print their own shape. There is no aimux status.
  • Logs in four places. Three processes log under ~/.aimux/logs/; the collector logs under ~/.claude/logs/ and is named differently from the rest.
  • One flat folder. ~/.aimux/ holds about forty items at one level: state, locks, caches, databases, settings and dated backups.

The design keeps the four processes and adds a thin layer: one status command, one health answer that every process gives in the same shape, one place per kind of file, and promote for all four. The status command comes first, because it needs nothing else to exist:

tool gateway: 1 of 5 backends down (slack)        aimux mcp proxy status

What makes it dependable rather than only tidy:

  • Always all four lines, in the same order, with the same four words for state: ok, degraded, down, not installed.
  • Every problem comes with one command that fixes it or shows more.
  • It cannot hang. Each process gets two seconds to answer; one that stays silent is shown as down and the other three still print. Asking never restarts or changes anything.
  • The exit code is the answer: 0 when nothing needs attention, 1 when something does. A script or the dashboard reads the same facts as JSON.
  • One build is the normal state. All four run the same program file, and one command upgrades them: it tests the new build on spare ports, swaps the file once, then restarts the processes one at a time, checking each is healthy before moving on and putting the old build back if one is not. A process with sessions connected to it waits for a quiet moment, or for your go-ahead, and shows as "restart pending" until then.
  • A different build is either brief or deliberate, and says which. During an upgrade it reads "restart pending". A process you keep on another build on purpose reads "pinned" and is not a problem. Anything else is drift and appears under "needs attention" with its fix. Files that two processes share carry a format number, and a process that meets a newer one than it knows refuses to write.
  • Details stay in the per-process commands. This one only tells you whether to look.

The four chokepoints

The green band deserves a closer look, because the design is about it. Four places already stand between an agent and the world, and three of them are among the largest components in the codebase.

model proxy
Port 7385. Only sessions started in a claude-codex shell send their model calls here. A normal Claude Code session talks to Anthropic directly and never touches it; aimux learns about those calls afterwards, from the telemetry Claude Code sends to the collector. For the calls it does carry, it records outcome, tokens, latency and which conversation. 5,200 lines.
MCP proxy
Port 7381. MCP tool calls from sessions set up to use it. Holds the allowlist and the server supervisors. 25,000 lines.
tool gateway
Port 7390. Hands sandboxed agents a short list of tools you approved, instead of everything a server offers. Each approved tool is stored with a fingerprint of its definition (name, description, inputs); if the server later changes that definition, the gateway stops serving the tool until you look at the change and approve it again. It detects a changed tool; it does not prove a tool is harmless. 8,000 lines, and today only sandboxed agents go through it.
hooks
A mechanism of the harness, not of aimux, and the only place that sees Read, Edit and Bash with the session id, or can refuse one. aimux installs eight entries into Claude Code: two keep the MCP proxy in order, six drive the "waiting for you" alert on your phone. None records a tool call. Codex has hooks too, with nearly the same event names, and aimux installs none there yet.

Below them sits a mature half you have already built: an OTLP receiver, a span store, a trace view with inline diffs, GOOD / BAD / WASTE labels, cost pricing, and export to MLflow, Jaeger or JSONL. Nothing new is needed to view or ship events.

The gap, in one picture

Four paths, four answers

The asymmetry is sharper than it looks. The environment that holds your credentials and your filesystem is the least governed; the isolated one is the most.

What happensCrossesRecordedCan be refused
A model call in Codex modemodel proxyyes, one lineno
An MCP tool call, local sessionMCP proxycounters onlyallowlist, static
Read, Edit, Bashnothing aimux ownstotals only, afterwardsyour own hooks, not aimux
A tool call inside a sandboxtool gatewaytext log lines; the sandbox keeps its own logtoken scope, allowlist, pin

Row three is the one that matters most: those are the majority of what an agent does. They are already counted: Claude Code reports each tool use to the collector, which keeps, per session and per tool, the number of calls, the tokens and the cost. What is missing is the single call: which tool, when, in what order, how long, and whether it was allowed. The file and the command themselves stay in the transcript, and the record points to the place. That is what the reporting hook adds. Refusing a call would be a separate, earlier hook, and is not part of the first release. Row four is what rows one to three should look like.

The idea

One event shape, emitted wherever a crossing happens, written once and rendered twice.

Three properties are worth insisting on. The record holds shapes, counts and outcomes, never prompts or tool arguments, which is already true of the model proxy's history. The ledger is the one authoritative copy, so a disagreement between views has an answer. And a dropped event is counted and shown, because a governance layer that quietly loses records is worse than none: it reports compliance it cannot back.

Can everything be connected?

Yes, and the connection is a few small labels each line carries: which conversation, which turn within it, and which call (plus a run label that ties together the three helpers of one Wingman question). Here is one turn as the ledger would hold it. Different writers produced these lines, each in its own file, and the labels are what make them one story.

Only the conversation label exists today, as a short tag in the model proxy's history. The turn and call labels are new, and agreeing exactly where each writer gets them is the first piece of work, before any ledger code. One rule keeps the count honest: every tool call has exactly one line that counts. Where a hook reports the call, that line is the record; the MCP proxy's line for the same call is kept only as a cross-check. So a call can never be counted twice, and a line whose labels are missing is shown as unmatched, never guessed into a turn.

One door, many engines

Codex mode is the first thing the model proxy does, not what it is for. The proxy is one door that Claude Code talks to, with several engines behind it and a router that picks one. An engine is anything that can answer: a model service, or another agent program running its own loop. Codex is already the second kind.

One rule about failure. If the proxy is down, a session that goes through it stops with a clear message. It is never quietly sent straight to the provider, because that would change both what is governed and what you are billed for.

Why Anthropic comes second. Today only sessions you start in Codex mode go through the proxy; a normal Claude session never touches it. Passing Anthropic's calls straight through changes that: every model call crosses one door, so the meter counts all of them and the router can choose for all of them. One thing is untested: whether your Claude subscription login works when Claude Code is pointed at a local address. That test is moved to the very start of the work, beside aimux status, because routing and half of what the meter can see depend on it. If it fails, direct Claude calls stay known only through telemetry.

When the choice is made

At the start of a session, not on every request. Changing engine in the middle throws away the open conversation and sends the whole history again, about 36 seconds instead of 5. So for a terminal session the choice is made once, at the start; for Wingman it is made per helper, each time. A switch in the middle is the exception: you ask for it, or a limit error arrives and you had opted in to falling back.

The right model for each task, without losing context

Context is never lost by changing model: Claude Code holds the whole conversation and sends it with every request. What a change costs is warm-up, because a model that has not seen the recent turns must read them first. The design pays that rarely, in four levels built in order:

LevelHow it worksWarm-up cost
1. By handYou change the model inside a session, as you do today. The proxy sends the next request to that engine.Paid once per change
2. By roleHelpers that already run as their own conversations (subagents, background calls) each get the engine that suits them. Your main conversation stays where it is.None
3. Both sides kept warmThe engine you left keeps its place for a while. Coming back, it only reads the turns it missed.Small
4. AutomaticYou pick "auto" as the model, and aimux chooses for the task.Paid only when worth it

A written catalog. One file says what each model is good at, what it is weak at, its speed and cost, and where each claim comes from. aimux models prints it. The router reads the same file, so what you read and what it does cannot drift apart. It starts from public benchmarks, marked as such, and is replaced by measurements from your own sessions.

Who decides when you pick auto. You write the rules in that file and the proxy applies them: the role, what the task needs, the allowance left. No model makes the choice. When the rules do not settle it, the route function Wingman already uses names the kind of work, once per task, and your file turns that into a model. Auto never interrupts a turn, leaves your main conversation alone unless you allow otherwise, says in one line what it chose, and is overridden the moment you name a model.

How it improves. Whether you kept a choice or changed it, your labels, and your own cases replayed on each model all feed the catalog's numbers. Changing what auto does remains a change you make to the file.

Switching a session that is already running

The switchWhat is copiedWhat it costs
Same program, other engine: Claude Code moving between Anthropic and CodexNothing. Claude Code holds the transcript and sends it with each request.One full resend of the conversation, then fast again.
Other program: Claude Code to Codex's own terminal, or backThe whole history, into a new session that points back at the old one.A new session; the two are recorded as one piece of work.

"The whole history" is delivered in three layers, because keeping everything and fitting everything into the model's working memory are different promises:

  1. Nothing is lost. The original transcript stays put, and the new session can read any part of it on demand. The reading tool that exists today is not enough: it cuts long exchanges and leaves out tool results, so this needs a reader over the transcript file itself.
  2. As much as fits, word for word. The newest exchanges are loaded in full up to a set share of the new model's working memory. Only what does not fit is summarised, and the summary says how much it stands for.
  3. A true conversion where the target can take it. The proxy already rebuilds a Codex conversation from a full Claude transcript whenever it starts one. A handoff to Codex reuses that. Those conversations are temporary today, so a handoff needs one that Codex keeps; whether Codex's own terminal can then reopen it is untested, as is the opposite direction.

A session longer than the new model's working memory cannot be held whole by any program; Claude Code summarises in the same situation. The first layer is what makes that safe. Every switch is written down: from which engine, to which, who or what asked, and what the resend cost.

Three safeguards apply to every switch. It happens only between turns, never while a tool is still running. The old session stays usable until the new one has answered once. And the first time a project's conversation would go to a provider that kind of content has not been sent to before, you are asked; a rule cannot make that choice for you.

Built to be reused

There are three proxies today and there will be more. They share almost nothing: the same small jobs are written again in each. Checking a request's key exists in five places, writing lines to a log in nine, starting a listener in six, and answering a health check in only one.

What gets reused is a small base that every proxy stands on. A new proxy then writes only what is particular to the protocol it speaks.

The base, written onceEach proxy, written for its protocol
The listener and its key check, plus a guarded entrance a sandbox can reachThe protocol it speaks
The labels: run, conversation, turn, callHow it finds them in its own requests
Writing ledger lines, and counting any it had to dropWhich lines it writes
The allow-or-refuse checkWhere in its flow the check sits
The health answer that aimux status readsIts own detail
Install, upgrade, roll backIts engines or backends

Routing, the meter, traces and evals read the ledger. They never need to know which proxy wrote a line, and that is what lets a fourth proxy arrive without changing any of them.

The base is pulled out of code that already works, one piece at a time, each when its second user is being written. Nothing is built for a user that does not exist yet.

Wingman is the second user

Wingman is the browser side panel. aimux does its thinking: it picks a mode, starts sandboxes, and answers one question with three helpers (a planner that reads your work tools, a reader that searches the web, a writer). The work on how Wingman chooses its models, started in another session, is now part of this design. Compared with that work, this design had gaps, now closed:

  • Wingman does not go through the proxy at all today. Its sandboxes call Anthropic directly. When the planner hit Claude's weekly limit on 23 November, nothing could take over. The proxy gets an entrance sandboxes can reach, so Wingman's calls cross the same door.
  • One list of engines, not two. The other session had proposed a separate models file. The list stays with the proxy, and a Wingman profile just names which policy each helper uses.
  • Falling back when the limit error arrives. Claude does not report how much allowance is left, so the proxy also reacts to the error itself: only if you opted in, and always saying so.
  • Private data stays where it is allowed. The planner sees Jira and Slack; the reader sees the public web. Each engine is marked for whether it may receive private data, and a helper can only fall back to engines its data may reach.
  • One question counts once. The three helpers are three sessions; a shared run label ties them together.
  • The tool gateway writes ledger lines too. It already knows which session every call belongs to, better than any other part.

The two efforts would change the same files, so the engine work is done once, here, with Wingman as its second user.

What it buys you

  1. An answer to "why is this slow", in one command. Yesterday's bug needed an afternoon and a throwaway script. The same question is now aimux model proxy stats, and the second bug it found took minutes.
  2. Spend you can see per session and per project. Prices exist for the Claude models; the Codex models you use are not priced yet and show as "unpriced" until they are. Estimates are always labelled as estimates.
  3. Switching backend as a quota runs down. Your own goal. It needs two numbers that nothing currently produces together: what is left, and what each session is spending.
  4. Tool changes you notice. Pins already catch a server quietly changing a tool's schema, but only for sandboxes. Your local sessions have your credentials and no such check.
  5. Evals from real work. A labelled turn and its cost share one identity, so "this turn was bad, cost $1.40 and had two refused tools" becomes one record set rather than three.

What it costs

Four ways this could be worse than doing nothing, written down so they can be checked against:

A slower agent. The proxy adds about 33 milliseconds today, measured against a fake server that answers instantly. A step takes three to five seconds, so the proxy is under one percent of it; the rest is Codex and the model. Bookkeeping must not spend that budget. Rewriting the proxy in a faster language would recover a few of those milliseconds at the price of 5,200 lines and their tests, so the design does not do it. What moves the number is keeping the conversation open (five seconds a step instead of thirty-six), the Fast tier, and the effort level.

Silent bypass. A layer that misses Read, Edit and Bash would report compliance while governing a minority of the work. That is why the hook comes early rather than last.

Plumbing nobody looks at. The first steps produce data, not features. If you never run the command, the work was wasted, which is the argument for stopping after the visibility release and checking.

Quietly becoming a product. Multi-tenant, always-on, cluster-deployed agent governance is OpenShell and OCE, your day job. If this starts needing an operator and roles, that is a choice to build a different thing, not a step to drift into.

One developer first

The control plane is your laptop, which is what the code already assumes: four launchd jobs, state under ~/.aimux, the key in the Keychain. Nothing else is ruled out; it is sequenced. Two habits keep the door open at no cost today: components take an address rather than assuming localhost, and every event carries the host.

LaterWhat keeps it cheap to add

One simplification is taken deliberately and written down: one machine, with one writer per ledger file. That is the first thing a second form factor would force us to revisit.

The order of work

The order in the spec is now: first a test of whether your Claude login works through the proxy, aimux status, and a short written contract for the labels. Then the visibility release, steps 1 to 4, where nothing is refused or switched. Then costs, traces, rules, and engines with routing. Evals run alongside, built by the eval session. Routing on cost and quality, moving a session to another program, and the full upgrade command are deliberately left for later.

What I need from you

Nothing has been built from this design. The open questions have grown and are kept up to date in the one-page version and at the end of the spec. The main ones:

  1. Is the evaluation plan still the plan? It is now written into the spec and has been checked by the eval session. Still yours to confirm: that session-to-evals and continuous learning both move into aimux, and that eval work starts with the corrections format.
  2. Does the hook refuse, or only report, in its first version? Report-only is safer and still gives the meter its attribution. Refusing puts aimux in the path of every built-in tool call.
  3. Answered: native Codex sessions are in scope. Codex has its own hooks, so the design installs aimux's hooks per harness, through one small installer with a Claude Code and a Codex implementation.
  4. Where would a Claude-side remaining allowance come from? The Codex side is polled every two minutes. Nothing equivalent exists for Claude, so quota switching would start one-sided.

If the programme is more than you want to commit to, approving the first steps and the visibility release (steps 0 to 4) and leaving the rest as recorded direction is a reasonable place to stop.
