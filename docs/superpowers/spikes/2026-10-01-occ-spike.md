## Findings

### 1. Docker compute cannot deploy agents

`DockerComputeDriver.validateHarnessAuth` rejects every harness auth binding. `docs/flows/docker-compose-development/agent-execution.md` step 8: "Deployment requires Agent `harnessAuth`. The Docker Driver rejects bindings, so deployment cannot queue a new AgentRevision." Only Kubernetes compute deploys agents. SSH compute exists (`drivers/compute/ssh/index.ts`) but accepts only embedded OpenClaw with operator-managed host credentials and has no dev profile.

The handoff's plan ("run OCC locally with the Docker compute driver") is not viable.

### 2. Gateway is per agent, not per namespace

`docs/guides/deploy/workspace-routing.md`: Kubernetes Compute provisions each Agent's HTTPRoute at `wss://<hostname>/namespaces/<namespaceId>/agents/<agentId>`. The handoff assumed one gateway per namespace. Correct model: one OpenClaw gateway process per agent revision, fronted by a shared private Envoy.

### 3. Gateway is private by design

Same doc: the chart creates a shared Gateway, ClusterIP EnvoyProxy and API-key SecurityPolicy. "No public listener is created." Routing is off by default (`gatewayRouting.enabled: false`). Exposing it outside the cluster is the operator's job (own Route/LoadBalancer + TLS).

### 4. OCC's own client does not use the gateway from outside

`scripts/first-agent-model.mjs` verifies a model turn by `kubectl exec` into the gateway pod, reading `OPENCLAW_GATEWAY_PASSWORD` from pod env, and POSTing to `http://127.0.0.1:8080/v1/chat/completions` inside the container. The reference client needs Kubernetes exec rights, not an OCC credential.

Agent gateway config written by that script: `gateway.bind: lan`, `auth.password` from env, `http.endpoints.chatCompletions.enabled: true`, `controlUi.enabled: false`. So the gateway speaks OpenAI-compatible chat completions over HTTP plus the OpenClaw WebSocket protocol.

### 5. OCC API has no session surface

`occ` CLI commands: agent, configuration, credential-source, dev, iam, installation, namespace, secret. No session/chat/message routes in `apps/controller/src`. The only `/v1/sessions` paths belong to the GitHub repository credential broker. Gateway state dirs: `/gateway-state/workspace` (embedded) and `/gateway-state/sessions` (dedicated) on the agent's volume.

### 6. The one OCC-mediated interactive path: native admin UI

`apps/controller/src/gateway/native-admin-proxy.ts` proxies HTTP and WebSocket from the OCC API to the agent's gateway via Envoy, with 25s WS leases and close reasons (`session_expired`, `revision_changed`, ...). Constraints (`docs/guides/deploy/native-admin.md`): trusted-operator pilot only, requires `administer` on the exact agent, OCE console browser session, per-agent wildcard DNS host. Not a programmatic client API.

## Implications for aimux

1. aimux needs two connections, confirmed, but the second one is per agent, not per namespace: OCC REST (agents, deploy, revisions, status) plus a per-agent gateway endpoint (sessions, events).
2. OCC will not hand aimux a reachable session endpoint. aimux must be configured with an operator-exposed gateway URL, or use port-forward/exec. A "connect to my OCC" UX that just takes an OCC URL + service key cannot open sessions.
3. Two gateway credentials exist (Envoy API key on the routed path, gateway password direct). Neither is issued per user by OCC.
4. Per-agent gateway means session list is per agent; a namespace-wide session view means fanning out across agents.

### Sessions (gateway, from laptop)

Path: `kubectl port-forward` to the gateway pod, `POST /v1/chat/completions`, `Authorization: Bearer <gateway-password>`. Unauthenticated request: 401.

| Turn | TTFT | Total |
|---|---|---|
| First request on fresh gateway (non-stream) | 8.72s | 8.72s |
| New session (user A) | 2.93s | 3.22s |
| Same session (user A recall) | 2.52s | 2.84s |
| New session (user B) | 4.69s | 5.10s |
| First request after redeploy (user A recall, non-stream) | 6.58s | 6.58s |

- Sessions are implicit: the OpenAI `user` field keys them (`agent:main:openai-user:<user>`); no `user` gives a one-shot `agent:main:openai:<uuid>`. No create call.
- Isolation: user B could not see user A's context. Continuity: user A recalled its word, including after redeploy.
- Sessions live on the per-agent `gateway-state` PVC (10Gi RWO) and survive revision changes. `openclaw sessions --json` inside the pod lists them.
- Gateway password is stored in Secret `openclaw-agent-transport-<hash>` (keys `gateway-password`, `app-server-token`) and did not change across revisions.
- Port-forward pins one pod; it breaks on every redeploy (also via `svc/`). aimux must reconnect on revision change.
- About 4.2k tokens per trivial turn (system prompt overhead).

### OpenShift adaptations needed (not documented by OCC)

1. All OCC pods pin `runAsUser: 1000`: grant `nonroot-v2` SCC to service accounts in the platform namespace and in every OCC-created `oce-*` namespace.
2. DNS egress is hardcoded to port 53; OpenShift DNS pods listen on 5353. Add an egress policy for 5353 in each namespace.
3. The OCC API listens only on the pod IP, so `kubectl port-forward` to it fails. Needs a relay pod (the dev profile ships one) or a Route.
4. Tenant pods pull from the platform namespace's ImageStreams: grant `system:image-puller`.
