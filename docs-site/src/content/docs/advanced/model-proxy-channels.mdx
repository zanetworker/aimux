description: Test changes on port 7386 without interrupting Claude Code sessions on port 7385.

The macOS stable proxy runs on `127.0.0.1:7385` under the `com.aimux.model-proxy` LaunchAgent. Its program is `~/go/bin/aimux` until `aimux upgrade` has moved it, and `~/.aimux/services/model-proxy/aimux` afterwards. `claude-codex` uses that listener. Do not replace the binary or restart the job while a Claude Code session uses it. Other aimux commands may use the same binary, so avoid installing an unrelated build to that path.

## Test on the dev channel

With the dashboard assets built, run this from the development worktree:

```bash
scripts/model-proxy-promote build-dev
aimux-dev model proxy serve --port 7386
```

In another terminal, run `claude-codex-dev`, then `claude`. In your shell setup, define `claude-codex-dev` to call your existing `claude-codex` function with `AIMUX_MODEL_PROXY_PORT=7386`. Both channels use the existing `aimux-model-proxy` Keychain entry. Only the stable listener publishes the Codex usage snapshot for the HUD. Images reach Codex on both channels: pasted screenshots, images in earlier messages, and images a tool returns (such as `Read` on a PNG), from base64 data or an https URL. An image block without a usable source is replaced with a short note, so a session never gets stuck on it.

## Check that it is healthy

```bash
aimux model proxy status            # the stable listener on 7385
aimux model proxy status --port 7386  # a dev listener
```

It prints the proxy's state and uptime, whether its Codex app-server is running, how many turns it has sent to Codex and how the last one went, and the same for the rate-limit checks behind the usage snapshot. Those checks cost no tokens, so a recent one shows the Codex login still works; only the stable listener makes them. Asking costs nothing and never starts Codex. The proxy starts Codex itself when it starts and writes how long that took to its log (`model proxy: Codex started in 3636ms`), so the first request does not wait for it. If the start fails, the log says why, the proxy keeps serving, and the next request starts Codex again.

The command exits non-zero when the proxy is degraded or not running, so a monitor can act on the exit code. The proxy is degraded when its most recent turn failed, or its most recent rate-limit check failed; a later success clears it. A request Claude Code malformed is not counted, and neither is a turn you interrupted.

The same report is `GET /health` on the proxy, as JSON: 200 when healthy, 503 when degraded. `GET /health` requires the proxy key, like every route but one. `GET /healthz` is that one exception: it needs no key and always answers 200 with less: the service name, `ok` or `degraded`, the build, the start time and the last successful turn and the ledger's line counts, without error text or request counts. `aimux status` reads `/healthz`.

## The ledger

Besides its request history, the proxy writes one line per model call to `~/.aimux/ledger/model-proxy.jsonl` (a proxy on another port writes `model-proxy-<port>.jsonl`, so the dev listener has its own file). The folder and the files are readable by you only.

A line says how a call went and never what it said. It holds the session id, a turn number, an id for the call, the model the client asked for and the model that answered, the engine, token counts, time to first byte, duration and the outcome. It holds no prompt, answer, tool argument or path.

| Field | Meaning |
|---|---|
| `session` | The harness's session id, in full. Taken from the request's metadata, or from the `X-Claude-Code-Session-Id` header |
| `turn` | The user request this call was made for, counted from 1 per session. Every model call made for one request, a subagent's included, carries the same number |
| `aimux.side`, `aimux.agent` | The call came from a subagent (with its id) or carried no session in its metadata |
| `gen_ai.request.model`, `gen_ai.response.model` | The model named by the client, and the one that answered. On Codex, a Claude model name is answered by the default Codex model, and both are kept |
| `gen_ai.usage.input_tokens` | The whole prompt. The part read from a cache is included, and also given as `aimux.usage.cache_read_input_tokens` |
| `aimux.usage.cache_write_input_tokens` | The part of the prompt written to a cache, also included in the input tokens. Anthropic reports it; Codex does not |
| `aimux.usage.unknown` | The answer carried no token figures, so the counts on this line are absent, not zero |
| `aimux.outcome` | `ok`, or the same word the request history uses for a failure |

A line of kind `switch` is written when a session's main conversation is answered by another engine than its previous request was: it carries the session, the turn, `aimux.from_engine` and `aimux.to_engine`. A subagent's call on another engine is not a switch.

A request the proxy rejects before an engine sees it is not a model call and writes no line.

Writing the line never changes the answer: it happens after the response, and a write that fails is counted, not reported to the client. `aimux model proxy status` shows a `Ledger` row (`latest line 1840`, or `latest line 1840, 3 not written`, or `off` when the file could not be opened at start), and `aimux status` lists a lost line or a ledger that is off under what needs attention. The keyed `GET /health` carries them as a `ledger` object (`seq`, `failed`, `off`), and the keyless `GET /healthz` as `ledger_seq`, `ledger_failed` and `ledger_off`.

The request history and `aimux model proxy stats` are unchanged.

## A second engine: Anthropic

`aimux model proxy serve --anthropic` adds a second engine. It is off unless the flag is given, and with it off nothing below applies.

With it on, the proxy decides who answers from two things a request carries, never from the prompt: the model it names, and its credentials.

| The request names | and carries | Answered by |
|---|---|---|
| a `codex:` model | the proxy key | Codex |
| a `codex:` model | no proxy key | nobody: 401, saying the session needs the proxy key in its base URL |
| any other model | the caller's own Claude login | Anthropic |
| any other model | the proxy key and no login | Codex, as before: the default Codex model answers |

A request to Anthropic is sent to `https://api.anthropic.com` and nowhere else, with its body unchanged, and the answer comes back unchanged. The caller's login travels in `Authorization` as Claude Code sent it; the proxy does not keep it, log it or write it to the ledger. The proxy key is removed before the request leaves, so Anthropic never sees it. Redirects are not followed.

The two credentials are different things. The proxy key says a caller may use what the proxy itself holds: the owner's Codex login, and the proxy's own routes such as `GET /health`, which stays local and still needs the key. The Claude login is the caller's own, and the proxy only passes it on to Anthropic. A request that is only passed on needs no proxy key: the login alone is enough, since the caller could have sent it to Anthropic directly.

A session that uses both engines has to present both, and `Authorization` is taken by the login. So the proxy key can also travel as the first part of the path: a base URL of `http://127.0.0.1:7385/k/<key>` puts it on every request. This way of presenting the key works whether or not `--anthropic` is given. The proxy removes that part before anything else reads the path. A wrong key there is refused even when a login is present, and so is the prefix spelled with percent escapes. A request whose address holds the key anywhere else is not sent to Anthropic.

Other paths Claude Code calls, such as `HEAD /api/hello`, are forwarded to Anthropic when the request carries a login, and are not found otherwise, as before.

A session can change engine from one request to the next, by naming another model. The conversation travels with each request, so the new engine reads what the other one wrote. One thing does not carry over to Codex: a block only Anthropic produces, such as a search it ran itself. Codex is given a short note in its place, naming the kind of block and nothing it held, and a tool only Anthropic can run is left out of the tools Codex is offered.

An Anthropic call writes a ledger line like a Codex call, with `aimux.engine` set to `anthropic`, the model Anthropic said answered, and the token counts from its answer. When an answer carries no token counts, an error for example, the line says so, and `aimux cost` reports how many such calls there were instead of counting them as zero.

The request history records an Anthropic call with the outcome `forwarded`. `aimux model proxy stats` was written for Codex conversations and lists every outcome it does not know under fallbacks, so forwarded calls appear there for now. Appearing there says nothing went wrong and nothing was sent twice; a forwarded call that did fail is counted as a failure like any other.

## Speed

The proxy asks Codex for the `priority` service tier, which Codex calls Fast. Measured on gpt-6.2-sol through the proxy: about 55 output tokens a second against 34 on the standard tier, so a 700-token answer arrives in 12 to 14 seconds instead of 22 to 24. It spends the plan's allowance faster; `aimux model proxy serve --service-tier standard` leaves Codex's own default in place.

Reasoning effort comes from Claude Code and is passed through unchanged (`--effort`, or `/effort` in a session): low, medium, high, xhigh and max all mean the same to Codex. A request for a `codex:` model that carries no effort runs at high, and a background request (any other model name) runs at low. gpt-6.2-sol's own default is low, so high costs time Claude Code did not ask for on simple steps: with a 150-token answer, medium on the Fast tier reached the first token in 2.3 seconds and finished in 4.4, against 2.9 to 3.2 and 6.8 to 7.2 at high on the standard tier.

The proxy itself adds about 33 ms to a request, measured against a fake app-server that answers at once; the rest of the wait is Codex and the model.

## Read what the proxy has been doing

Each listener appends one JSON line per answered `POST /v1/messages` request (not `/health` or `/v1/models`) to `~/.aimux/logs/model-proxy/requests.jsonl` (`requests-<port>.jsonl` for a dev listener): time, outcome, model, effort, status, time to first byte, duration and token counts, plus what a fallback says about itself. No prompts, answers or tool arguments are written. The file rolls over to `.1` at 8 MB and only that pair is kept, so the history covers roughly the last 50,000 requests rather than a fixed stretch of time, and never grows beyond 16 MB.

```bash
aimux model proxy stats --since 24h    # the stable listener
aimux model proxy stats --port 7386 --since 2h
aimux model proxy stats --since 6h --session 146917eb-1666-4076-9ba6-9c7cf9ccbf7a
```

It prints a row per outcome, slowest first, with counts, mean and 95th percentile duration, average prompt size and failures, then the fallback shapes. Read the outcomes in three groups. `hit_continuation` and `hit_idle` reused a thread, so the prompt was cached. `new_session` (a conversation's first request), `stateless` (a background request or one without a session id) and `invalid_request` (rejected before Codex saw it) are all normal. Everything else is a fallback: the thread could not be reused and the conversation was reprocessed, which is slow on a long one, so a large count there is worth investigating. When the window holds more than one conversation it also lists them, the costliest first, so one slow session is not hidden in an average. A conversation appears as a short one-way tag rather than its session id: `--session` takes either, hashing an id to its tag, and requests that carried no session id are grouped as `(no session id)`, which is worth noticing because they can never reuse a thread. Records written before this release carry no tag at all and are grouped separately as `(before session tags)`; they may well show thread reuse, so do not read them as sessionless. `jq` reads the same file for anything the summary does not cover.

## Check prompt caching

Claude Code requests with a `codex:` model and a session ID can reuse an ephemeral Codex thread while the conversation history, system prompt, and tools match. One handoff can return several `tool_use` blocks (calls Codex makes within 300 ms of each other), in streaming and non-streaming responses alike; the next request continues the same turn when the user messages added since the handoff carry a `tool_result` for every one of them, however Claude Code spreads them: one message with several results, one message each, or further user and in-conversation `system` messages (its hooks' reminders) after them. Text and images in those messages reach the turn as steering input. An assistant message among them is history the proxy did not produce, so it starts a fresh thread instead, as it does when a result is missing. A tool handoff waits for results for up to 10 minutes. The proxy releases idle threads after 30 minutes. Requests without a session ID and background requests use a fresh thread.

For the last model request Codex reports, `usage.input_tokens` counts uncached input and `usage.cache_read_input_tokens` counts cached input. Add them to get the full prompt size. In a session, `usage.output_tokens` sums the outputs reported during that Messages request.

The proxy logs the reuse outcome, token counts, and time to first byte on stderr for each Messages request. If a session hands off a tool before Codex reports usage, the response estimates the prompt counts from the last report on that thread and reports zero output tokens. The proxy logs these estimates as `usage=estimated` with `estimated_input_tokens` and `estimated_cached_input_tokens`. The counts start at zero on a fresh thread.

## Promote or roll back from a fresh terminal

The promote is the careful path for the model proxy: it tests a build before installing it. `aimux upgrade` installs the build you run without testing it; see [Upgrading the Background Services](/guides/upgrading-services/). The promote swaps whichever file the job runs, `~/go/bin/aimux` or the service's own copy once an upgrade has moved it.

Close stable Claude Code sessions and stop the hand-run dev listener first. In a fresh terminal outside Claude Code, run `scripts/model-proxy-promote promote`. The script runs the Go suite, channel tests, golangci-lint against the `origin/main` baseline, and the live Codex test. It then builds a candidate, starts it on `7386`, and checks a `claude -p` response through it. The live checks use your Codex allowance.

Only then does it back up the program the stable job runs to `aimux.prev` beside it, replace that program by rename, restart the LaunchAgent, and require authenticated HTTP 200 from `/v1/models` and one real answer through the stable port. The first answer after a restart has timed out on a good build, so a failed answer is asked for once more before it counts. If the stable check still fails, it tries to restore the backup. Run `scripts/model-proxy-promote rollback` from a fresh terminal to restore that backup manually. It restarts the same job and checks the same endpoint.

With a local `claude-hud` clone under `~/go/src/github.com/zanetworker/claude-hud`, `scripts/model-proxy-promote pin-hud [commit]` prepares a detached checkout at a committed revision (defaults to `HEAD`). Point your statusline wrapper at `~/.claude/claude-hud-pins/current/src/index.ts`. Promotion switches that pin after the proxy health check. To use a previous HUD revision, run `pin-hud` with its commit; proxy rollback only restores the executable.

Pin Codex with `brew pin --cask codex` for the Homebrew cask. To upgrade, unpin it deliberately, upgrade, pin it again, and rerun the live check before relying on the new version.
