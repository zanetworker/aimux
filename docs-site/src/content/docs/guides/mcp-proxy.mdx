---
title: MCP Proxy
description: Serve your stdio MCP servers lazily behind shared endpoints
---

Claude Code starts every configured MCP server when a session opens, before any tool is used. With many stdio servers that costs hundreds of MB to a few GB per session, and each session runs its own copy.

`aimux mcp proxy` puts your stdio MCP servers behind shared HTTP endpoints:

- **Lazy:** tools are listed from a cached catalog, and a server starts on its first tool call.
- **Shared:** one process per server serves every session.
- **Stopped when idle:** a shared server unused for 10 minutes (configurable) is stopped, including any child processes started by `npx` or `uv`. A per-session server (a browser) lives as long as the Claude Code process that uses it, as it would directly.
- **Current tool lists:** when a server starts and lists tools its catalog did not have (an upgrade added one), open sessions get the new list right away.
- **Same names:** each server keeps its own name, and every tool keeps its original name (`mcp__slack__post_message`, not renamed). Permission rules keep working unchanged.
- **Per-server endpoints:** each moved server is served at `/mcp/<server>` under its original name, so `~/.claude.json` has one HTTP line per moved server instead of one `mux` entry.

`install` also moves HTTP servers that need no OAuth (see [HTTP servers and the Keychain](#http-servers-and-the-keychain)); SSE servers and HTTP servers that sign in with OAuth stay direct.

The proxy can also serve a saved HTTP server: a definition under `httpServers` in `~/.aimux/mcp-servers.json` (kept apart from the stdio definitions in `mcpServers`, so an older aimux still reads the file and sees only stdio servers) with `"type": "http"`, its `url` and a reference per header (`"secrets": {"headers": {"Authorization": {"keychain": {"item": "aimux-mcp-proxy/<server>", "field": "headers.Authorization.value"}}}}`). The header values are not in that file; the proxy resolves each reference (a field of the Keychain item, account `aimux`) each time it starts the server, and its errors and status never carry a header value. A reference with no backend, or one this aimux does not know, fails that server's start with an error naming the server and header. When an HTTP server restarts and no longer knows the proxy's session (404, or FastMCP's 400 `No valid session ID provided`), the proxy opens a new session and sends the request once more.

`~/.aimux/mcp-servers.json` is generated state (`"schema": 2`, `"generatedBy": "aimux mcp proxy install"`): install and `aimux mcp proxy edit` write it; do not edit it by hand. An aimux reading a file with a newer schema refuses it ("written by a newer aimux"); a file without a schema (from before) is read as before. If that item is missing or locked, the server fails to start with `keychain item aimux-mcp-proxy/<server> is missing or locked`; the other servers keep working.

Only **tools** are proxied. Prompts, resources and log messages from the proxied servers are not available through the proxy; keep a server as a direct entry if you rely on those.

## Supported clients

The proxy is tested with Claude Code only (2.1.319). `install` moves the servers in `~/.claude.json` and nothing else; Codex keeps its own servers from `~/.codex/config.toml`, each Codex session still starting its own copies.

What is specific to Claude Code: the limits the proxy matches (a call may run as long as Claude Code's default `MCP_TOOL_TIMEOUT` allows, and install sets `CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT`), and how sessions end (the proxy follows the process that holds each session's connection, which assumes a client keeping its connections open while it runs, as Claude Code does). Codex speaks the same protocol, so pointing it at `http://127.0.0.1:7381/mcp/<server>` by hand may work, but its timeouts, session handling and progress use have not been tested; until they are, keep Codex's servers direct.

Protocol versions: the proxy's HTTP endpoints offer only the session-based MCP versions (2025-11-25 and earlier), because per-session servers such as playwright are started and stopped per client session. A client asking for the sessionless 2026-07-28 version is refused with the list of supported versions and must use one of them. Claude Code 2.1.319 asks for 2025-11-25.

## Switch Claude Code to the proxy

```bash
aimux mcp proxy install --dry-run   # what would change, names only
aimux mcp proxy install
```

`--dry-run` writes nothing outside a temporary directory. A server missing from the catalog is started once to list its tools into a temporary copy of the catalog; `~/.aimux/mcp-catalog.json` and `~/.aimux/mcp-servers.json` are not written.

`install` checks everything before it touches a file, and refuses with a message naming the problem:

1. It lists the tools of every server it will move into `~/.aimux/mcp-catalog.json`, so tools a server gained in an upgrade are exposed. After that, whenever a moved server starts the proxy lists its tools again, and open sessions get any new ones without a restart or a reload. A server that fails is refused by name; fix it or leave it direct with `--skip <name>`.
2. It saves the definitions (command, arguments and `env`) of the servers it moves in `~/.aimux/mcp-servers.json`, an owner-only file the proxy runs them from, and adds them to that file's moved list, which is what the installed proxy serves. They are saved with `${VAR}` and `${VAR:-default}` already resolved in your shell (and the proxy does not expand them a second time, so a value that itself contains `${...}` stays as it is), because launchd starts the proxy without your shell's variables. A variable a server reads from your shell without its entry declaring it is not there under the proxy: `podman run -e SLACK_XOXC_TOKEN ...` passes nothing, and a server that switches tools on by a variable offers fewer. Declare such a variable in the entry's `env` as `"NAME": "${NAME}"` before installing, or add it to a moved server with `aimux mcp proxy edit <server>`. The saved values are copies: after rotating a credential, update the moved server with `aimux mcp proxy edit <server>` (re-running install leaves moved servers as they are), or run `aimux mcp proxy uninstall`, update the direct entry and install again.
3. It starts the proxy under launchd (`~/Library/LaunchAgents/com.aimux.mcp-proxy.plist`, started at login and restarted if it exits, logs in `~/.aimux/logs/mcp-proxy/`) and waits up to 10 seconds until the proxy answers and has an endpoint for every server it will move. The plist sets `PATH` and `HOME` from your shell, so `npx`, `uv` and other tools resolve as they do there; it holds no other values. A proxy already running has its daemon reload in place, so open sessions keep their connections; the daemon restarts only when it crashes (launchd brings it back) or when the aimux binary itself is upgraded (install and `status` say when an upgrade restart is pending). When the launchd job runs another aimux binary than the one you run `install` from, install points the plist's program at this binary (nothing else in the plist changes), restarts the job so launchd runs it, and says which binary it ran before; this happens on every run, also one with no new servers to move.
4. It has the proxy start each server it will move and list its tools (the probe below, for those servers only). A server that fails under launchd is refused by name; fix it or `--skip` it.
5. After the switch it sets `CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT=1800000` in the `env` of `~/.claude/settings.json`, unless you set it yourself. Claude Code gives up on a tool call that stays silent for 5 minutes on an HTTP server but 30 on a stdio one; this gives calls through the proxy the stdio limit. It also applies to your other HTTP MCP servers. Uninstall removes it (only if install added it and you did not change it). Re-running install sets it even when there are no new servers to move, so an install from before this step gets it that way. When `~/.claude/settings.json` does not exist or cannot be edited, install leaves it out and says so; the servers are moved either way, and silent calls through the proxy then time out after 5 minutes.
6. It adds the two server hooks to `~/.claude/settings.json` (see [New servers after installing](#new-servers-after-installing)) and records that in the manifest; uninstall removes them. Re-running install adds them to an install from before this step.

If install stops before changing `~/.claude.json`, it says so, puts `~/.aimux/mcp-servers.json` and the launchd plist back as they were, and removes the launchd agent again when it was the one that started it; an agent that was loaded before is reloaded on its previous configuration. Taking removed servers off the proxy (a moved server whose entry you deleted from `~/.claude.json`) happens first, before the tool listing and probes, and stays done if a later step fails or is interrupted: those servers are gone from your config either way. `--dry-run` lists them ("Would take off the proxy").

Then it changes `~/.claude.json`, after backing it up to `~/.aimux/backups/` (owner-only, the newest 10 kept):

Each moved server's entry (stdio or HTTP) becomes `{"type": "http", "url": "http://127.0.0.1:7381/mcp/<server>"}` under the same name. HTTP servers kept direct stay as they are. aimux's own `aimux` stdio entry moves like any other. Nothing else in the file changes, not even spacing. The edit is atomic: one edit of `mcpServers`, so there is no half-switched state.

If a server's entry changes between these checks and the edit (another program saved `~/.claude.json`), the edit fails ("changed while installing; run install again") and the proxy's files are put back as above. An entry removed in that window is simply not moved, and the proxy stops serving it.

Just before the edit, install records it in `~/.aimux/mcp-proxy-install.json` (owner-only): for each server it moves its original entry and the entry install writes, the servers kept direct with `--skip`, and the proxy's port. If the record cannot be written, nothing is edited. If the edit does not land, the record goes back to what it was (or is removed on a first install). Because the record comes first, an install killed at any point can be undone with `uninstall`: entries the edit wrote get their originals back, and entries it never reached are left as they are. A later `install` with a different `--port` is refused, since the entries point at the recorded one; uninstall and install again to change the port. A repeat `install` with nothing new to move leaves `~/.claude.json` alone and says so; it still takes off the proxy any moved server whose entry you removed from `~/.claude.json` (its saved definition and manifest entry go, and the daemon reloads in place), and sets `CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT` in `~/.claude/settings.json` and records that in the manifest when it is not there yet (step 5).

Install says how many Claude Code sessions are open. **Sessions already open keep their direct servers until they restart**, and one that saves its settings later can write the old entries back; `status` calls that drift.

| Before | After |
|---|---|
| `mcp__slack__post_message` | `mcp__slack__post_message` |
| `mcp__aimux__list_sessions` | `mcp__aimux__list_sessions` |

Tool names stay the same, so permission rules keep working unchanged.

### Switch back

```bash
aimux mcp proxy uninstall
```

`uninstall` undoes what the manifest records, in one edit of `mcpServers`: each moved entry that is still the proxy entry install wrote gets its original bytes back; one you changed or removed since is kept as it is and reported. Servers you added after installing stay. When nothing else changed, the file comes back byte for byte. It also deletes the moved servers' saved definitions (they hold resolved `env` values) from `~/.aimux/mcp-servers.json`, then removes the manifest and the launchd agent. If `~/.claude.json` is gone, every entry is reported as removed and the rest still happens. Running it twice is harmless. If the agent cannot be removed, the config stays restored and running `uninstall` again removes it.

Without a manifest, `uninstall` leaves the Claude config alone and removes a leftover launchd agent if there is one. To restore entries by hand, copy only their `mcpServers` entries from a backup in `~/.aimux/backups/`: copying the whole file would also undo everything Claude Code saved since. In the backup install wrote, a moved HTTP server's header values are `"[in Keychain]"`; read them from the item with `security find-generic-password -a aimux -s aimux-mcp-proxy/<server> -w` (it prints the item's JSON, whose `value` fields are the header values), or run `uninstall` with the manifest in place, which puts them back itself.

### New servers after installing

Install also adds two Claude Code hooks to `~/.claude/settings.json` (backed up first; your own hooks and other aimux hooks are kept), so new servers do not quietly stay direct:

- **When a session adds a server.** After a Bash call that runs `claude mcp add`, `claude mcp add-json` or `claude mcp add-from-claude-desktop` and succeeds, aimux moves the servers still direct behind the proxy (stdio, and HTTP servers that need no OAuth), as `install` does (and names any HTTP server it left direct, with the reason), and the session shows: `foo moved behind the aimux proxy (tools unchanged; it starts on first use). Open sessions keep their direct copy until they restart.` If the move fails, nothing changes and the message names the server that failed and why (`--skip <name>` keeps one direct). A server added for one project only (`claude mcp add` without `--scope user`, or a repo's `.mcp.json`) is not moved, because the proxy shares user-scope servers; the message says how to re-add it at user scope. The add is recognised as a command of its own, also after `NAME=value`, `env`, `command`, `exec`, `nohup` or `time` and across a line continuation, but not inside quotes, a comment or a heredoc body. A project-scope explanation looks at the session's folder, not a `cd` earlier in the same command line; anything the hook misses is named at the next session start.
- **When a session starts.** aimux reads `~/.claude.json` and its install record (no server is started) and, only when some stdio or movable HTTP servers are still direct, shows one line (servers that need OAuth are not named): `2 MCP servers are not behind the aimux proxy: foo, bar. Run aimux mcp proxy install.` This catches servers added in a terminal, by hand or by a script, where no session hook runs. When a moved server's entry has drifted back to its direct command, the same line says so: `Running direct again instead of through the aimux proxy: foo; to fix it, ...` with the fix from [Drift](#drift). Servers defined only for the current project (which the proxy cannot share) are named to Claude, not in your line: `Project-only MCP servers here (not shared by the aimux proxy): baz.`
- **When the proxy is down at session start.** If any moved server's entry in `~/.claude.json` still points at the proxy (entries you removed or that drifted back to a direct command do not count) and nothing answers on its address within about 1 second (connection refused or timed out, for example during `aimux mcp proxy restart`), the hook shows one line first, on its own, before the line above:

  ```text
  aimux MCP proxy is not answering on 127.0.0.1:7381, so this session's proxied MCP servers will fail. Fix: aimux mcp proxy restart, then /mcp Reconnect (or restart this session).
  ```

  Claude Code does not retry a server that failed at session start, so after the restart reconnect each server in `/mcp` or run `claude --resume`. When the proxy answers, the hook adds nothing. The check is a TCP connect to `127.0.0.1` only; it sends no request and reads no secret.

A hook never fails a tool call or a session start. `aimux mcp proxy status` shows whether the hooks are on, and `uninstall` removes them (and nothing else in your hooks). They run alongside hookify or any other hooks you have: hookify rules can warn about or block a command, these move servers and report.

A stdio or HTTP server added to `~/.claude.json` after install runs directly until it is moved. To move it by hand:

```bash
aimux mcp proxy install
```

Running `install` again moves only the stdio and HTTP servers not yet moved and not kept direct (by `--skip`, or because they need OAuth or are down) (same refresh, daemon prepare and probe, then one atomic edit of just those entries) and adds them to the manifest. The daemon reloads in place, so open sessions keep their connections. Servers already moved are left alone. It also tidies up: a moved server whose entry you removed from `~/.claude.json` (for example with `claude mcp remove <name>`) is taken off the proxy (its saved definition and manifest entry go, and the daemon reloads in place). With no new servers to move, install still does that, sets `CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT` in `~/.claude/settings.json` if it is not there yet (step 5 above), adds the two server hooks if they are missing (step 6), and changes nothing else.

### Changing a moved server

Once moved, a server's command, arguments and `env` live in `~/.aimux/mcp-servers.json`. Editing `~/.claude.json` no longer changes the server. To change a moved server:

```bash
aimux mcp proxy edit <server>
```

This opens the server's definition in `$EDITOR` (an owner-only temp copy that includes its `env`; `vi` when `$EDITOR` is unset). `$EDITOR` may carry arguments, such as `code --wait` or `vim -n`; it is split into words as a shell would split it (single and double quotes and backslashes work, variables and globs are not expanded), and the temp file is passed as the last argument, so quote a path with spaces: `EDITOR='"/Applications/My Editor/bin/ed" -w'`. When the editor exits, `edit` validates the definition (valid JSON holding only `command`, `args` and `env`, a command found on the proxy's `PATH`) and probes the server with it the way launchd runs it: `PATH` and `HOME` from the installed launchd plist plus the definition's `env`, nothing else from your shell, with a bare command resolved on that `PATH`. A definition that only works because of a variable or a `PATH` entry in your shell fails here. Without an installed plist, `edit` says so and uses the `PATH` and `HOME` install would write from your shell. A server that starts and initializes passes even if it lists no tools. Only then does it write the definition to `~/.aimux/mcp-servers.json`, record the tools it listed in the catalog, and reload that one server in place. On any failure before the write the old definition stays. An unchanged definition saves nothing. If the reload fails after the write, the new definition takes effect when the proxy next starts. Env values are never printed. `edit` waits for no other run: while `install` or `uninstall` runs it refuses.

The temp copy is removed when `edit` ends, also on Ctrl-C or `SIGTERM` after the editor closed. Some editors write swap or backup files beside it (vim's `.swp`, a `~` backup); those hold the same `env` values, so configure your editor not to keep them for files in your temp directory, or delete them.

The fallback: `uninstall`, edit `~/.claude.json`, `install`. `edit` changes stdio servers only and refuses an HTTP one (`<server> is an HTTP server; aimux mcp proxy edit changes stdio servers only`).

### Drift

```bash
aimux mcp proxy status
```

`status` reads the running proxy's `/status` on `127.0.0.1` and prints tables: the proxy and tool gateway rows, then the servers with a count line under them, their errors, and last one row per thing to know. Its `WARNING` rows are what needs you (entries that drifted from their proxy URL because a running session saved a stale copy or you edited them, stdio and HTTP servers not behind the proxy yet, an upgrade restart pending), each with its fix; its `INFO` rows say how many servers `install` moved (`--json` names them in `install.moved`) and which HTTP servers are kept direct, with their reason. [Check its health](#check-its-health) shows the page. Not running is reported, not an error. A failed server's error says how long ago it failed (the `AGE` column), so an old failure is not read as live; the next call starts the server again. The `gateway` row says how long the worker has run, and one warning names the backends that are down, each with when it was last checked (`2 gateway backends down: wiki (checked 40s ago), slack`; the worker retries a down backend every minute).

Drift: a moved server's entry is no longer its proxy URL. To fix it:

```bash
aimux mcp proxy uninstall
aimux mcp proxy install
```

### HTTP servers and the Keychain

`install` moves an HTTP (Streamable HTTP) server when it needs no OAuth: no auth at all, or a static `headers` map. Before moving, it sends each such server one MCP `initialize` request (5 seconds each, in parallel):

| What it finds | What install does |
|---|---|
| The server answers | Lists its tools and moves it; one that answers but cannot list its tools fails install by name, as a stdio server does (fix it or `--skip` it) |
| `401` with a `WWW-Authenticate` challenge, no headers | Keeps it direct: `kept direct: <name>: needs OAuth (later)` |
| `401` with a challenge although it has headers | Keeps it direct and records it for that URL and those header names (a hash; no values): `the server refused its headers (401)` |
| Refused, DNS failure, `502`, `503` or `504`, or no answer in 5 seconds | Keeps it direct for this run (`not reachable now; run install again when it is up`) and tries again next time |

An entry with an `oauth` field, a `headersHelper`, `type: "sse"`, a header value that is not a string, a `${VAR}` in a header that is unset in your shell, or a `${VAR}` anywhere in its URL (`uses ${NAME} in its URL; keep it direct until Plan 4c`: the URL is saved as written, and a resolved value could be a secret) stays direct with that reason. A secret written literally in a URL's query or userinfo cannot be told apart, so the proxy hides every query value and userinfo password of a moved server's URL in its errors and logs, as it does header values (also in their URL-escaped and JSON-escaped forms, and a `Basic` header's decoded `user:pass`). If the running proxy is another aimux version (an upgrade restart is pending), `install`, `edit` and `refresh` refuse whenever HTTP definitions are involved (servers this run moves, or ones already saved), headerless ones included. The message names the binary the proxy's launchd job runs (from its plist): update that binary to this version and run `aimux mcp proxy restart`, or run `install` from this binary (it switches the job to this binary and restarts it before this check), because `edit` and `refresh` make a running proxy reload rather than restart, and an older proxy may not read the definitions' header references. A server with headers moves only on macOS, and only when its header values fit one Keychain item (about 1.9 KB in all; a longer one stays direct with `header values too long for the Keychain`).

`aimux mcp proxy status` lists the servers kept direct by reason (`kept direct: needs OAuth (later): granola, ...`) as `INFO` rows, from your config and what the last install recorded (servers that need OAuth and servers that refused their headers); it never contacts the servers. A movable HTTP server not moved yet (one that was down, one whose URL or header names changed since install recorded its refused headers, or one from before install recorded them) is a `WARNING` with the stdio ones under not behind the proxy, and the session-start hook names it; recorded servers are named in neither. Running `install` again checks them and records the reason.

A moved HTTP server's entry becomes the same proxy entry a stdio server gets, so tool names and permission rules do not change. Its header values go into the Keychain item `aimux-mcp-proxy/<server>` (account `aimux`; the value goes to `security` on stdin, never on a command line). `${VAR}` and `${VAR:-default}` in header values are resolved in your shell when you install; the item also keeps the text as written (`Bearer ${TOKEN}`), so `uninstall` puts the entry back byte for byte. To change a header value, uninstall, change `~/.claude.json` and install again.

The values are never written anywhere else aimux keeps: `~/.aimux/mcp-servers.json` holds the URL and a Keychain reference per header, the manifest holds each original entry with `"[in Keychain]"` in place of each value, and the backup install writes of `~/.claude.json` has the same placeholder. Older backups in `~/.aimux/backups` from before the move still hold the values; install names them once (`note: ... still hold header values for <names>; delete them with: rm ...`).

A server whose tool list echoes one of its secrets (8 bytes or more: a header value, a `Basic` header's decoded `user:pass` or password, a URL query value or userinfo password, each also in its URL-escaped or JSON-escaped form) is not stored: listing it fails with `its tool list contains one of its header values; not stored`, so install refuses that server by name (fix it or `--skip` it), because the tool list is saved in the catalog. Logs and errors never carry a header value either.

`uninstall` reads each item before it changes anything. If an item cannot be read (a locked Keychain), it stops with nothing changed and names the item. It deletes the item of each server it restores; a server whose entry you changed or removed since install keeps its item, and uninstall says which and prints `security delete-generic-password -a aimux -s aimux-mcp-proxy/<server>` to remove it.

If an item is gone (deleted, or a Keychain reset), uninstall cannot give that server its original back and stops, naming the way out: `aimux mcp proxy uninstall --without <server>` removes that server's proxy entry from `~/.claude.json` instead of restoring it, restores the others, and tells you to add the server again with `claude mcp add`. The backups do not help here: their header values are placeholders too.

Install records the manifest just before it edits `~/.claude.json`, after it has written the Keychain items. If it is killed between the two, the manifest lists servers whose entries were never switched: `uninstall` then finds each such entry still equal to its original, reports it as already restored, and deletes its item, so nothing is left behind.

### Skip servers

Leave specific servers as direct entries (stdio or HTTP, OAuth servers included, so they stay direct once the proxy can sign in):

```bash
aimux mcp proxy install --skip slack --skip github
```

The `--skip` choice is recorded in the manifest and kept on later runs until `--unskip`:

```bash
aimux mcp proxy install --unskip slack
```

### Reload and the restart trade-off

The daemon reloads in place when you change a server (`edit`) or move a new one (re-run `install`). It does not restart, except when `install` runs from another aimux binary than the launchd job: then it points the job at this binary and restarts it first. The daemon restarts only when it crashes (launchd brings it back) or when the aimux binary itself is upgraded.

Open sessions survive a restart. In a live check, a Claude Code session made a tool call through the proxy, the daemon was restarted with `launchctl kickstart -k` (the same restart launchd does after a crash), and the next tool call from that session worked, with no session restart. The first call after a restart starts that server's backend again, so it can take a moment longer.

`status` says when an upgrade restart is pending:

```bash
aimux mcp proxy status
```

To restart the daemon after an upgrade:

```bash
aimux mcp proxy restart
```

It restarts the daemon in place (`launchctl kickstart -k`: the launchd job stays loaded, and its plist is not re-read), waits until the new daemon answers on the port the proxy was installed on, and prints its pid and version; a restart that fails or times out says so (and a note if the daemon runs another aimux binary than the one you ran, which `aimux mcp proxy install` from the new one fixes). You can do this at a convenient time; open sessions keep working.

### Tradeoffs

| | Direct stdio servers | Through the proxy |
|---|---|---|
| Memory | one process per server per session | one process per shared server, stopped when idle; one per session for browser servers, until that Claude Code process exits |
| Session start | every server starts | nothing starts until a tool is called |
| First call to a server | immediate | waits for the server to start |
| Tool names | `mcp__<server>__<tool>` | `mcp__<server>__<tool>` (unchanged) |
| Prompts, resources, log messages | available | not available (tools only) |
| A server asking you something mid-call (elicitation), `roots/list` | answered by Claude Code | answered "not supported" |
| Progress of a long call | shown, and resets Claude Code's idle limit | relayed to the session that made the call, same effect |
| Longest call | Claude Code's `MCP_TOOL_TIMEOUT` (default about 27.8 hours) | the same default; a larger `MCP_TOOL_TIMEOUT` you set is not matched |
| Working directory of a server | the session's folder | `/` (a server that writes relative paths writes elsewhere) |
| Browser servers (`--per-session`) | one per session, until Claude Code exits | one per session, until that Claude Code process exits |
| A server crash | that session loses it | every session loses it until the next call restarts it |
| Needs | nothing | the launchd agent running |
| Permission rules | direct rule | same rule (no translation) |

## Set it up by hand

Without `install`, nothing edits your files:

1. Cache the tool catalog. This starts each stdio server in `~/.claude.json` once and stops it, and saves their definitions in `~/.aimux/mcp-servers.json`:

   ```bash
   aimux mcp proxy refresh
   ```

2. Run the proxy:

   ```bash
   aimux mcp proxy serve
   ```

3. Print the Claude Code entries and add them to `mcpServers` in `~/.claude.json` yourself (after an `install`, `serve` without `--only` serves only the moved servers):

   ```bash
   aimux mcp proxy config
   ```

Later refreshes merge: a server still in `~/.claude.json` overrides the saved copy, and one you removed is kept. To drop a server from the proxy, remove it from `~/.claude.json` and pass `--exclude` to `refresh`; while it is still in `~/.claude.json`, every `refresh` and `serve` adds it back unless you pass `--exclude` to each.

The catalog is also refreshed whenever a server starts, and tools it did not list before reach open sessions right away (the proxy reloads that server's tool list in place).

## The sandbox tool gateway

The proxy service has a second worker for OpenShell sandboxes: the read-only tool gateway on `127.0.0.1:7390`, which sandboxes reach as `host.containers.internal:7390`. It serves only the tools approved in `~/.config/aimux/tool-sets.yaml` (or, before `aimux servers migrate`, `tool-sources.yaml`), which list the tools a set may use, and only once each is approved into `~/.aimux/tools/pins.json` (see `aimux tools`); for an HTTP server in `servers.yaml`, only while the server's identity is the one the tools were approved under, so a changed identity holds them as `source_changed` even when their definitions match, while pins made before `servers.yaml`, which recorded the URL, still match at the same URL ([Servers](/guides/servers/#approvals-follow-the-server-not-its-url)), from its own pool of backends: it never shares a server process, a cache or an environment with the proxy on `:7381`, and each restarts on its own.

```sh
aimux mcp proxy gateway install    # run it under launchd (com.aimux.tool-gateway), at login and after a crash
aimux mcp proxy gateway status     # running or not (since when), live leases, backends, which are down and when each was last checked; a worker that is not running or does not answer goes to stderr, exit 0
aimux mcp proxy gateway uninstall  # stop it; Workspace turns then fail until it is installed again
aimux mcp proxy gateway serve      # run it in the foreground (what launchd runs)
```

`gateway install` and `gateway uninstall` take one lock (`~/.aimux/gateway-install.lock`): a second one while the first runs waits 3 seconds, then stops with a message. Run `gateway install` again from a new aimux binary to switch the worker to it: install rewrites the plist for the binary you ran, restarts the job (waiting for launchd to unload the old one first), waits up to 90 seconds in all (the worker opens its socket only after listing every backend; a rollback's check gets what is left) for the job's own worker (its pid is the one launchd reports, so a foreground `gateway serve` does not count) to answer on its control socket, and names the binary it ran before. When none answers, launchd refuses to load the new plist, or you press Ctrl-C while it waits, it writes the old plist back, loads it again and checks that worker in what is left of the 90 seconds, saying whether it answers or that this was not verified (no time left, Ctrl-C, or an older worker that reports no pid) (an upgrade in place, with the same binary path, can fail both ways); a first install that never answers is removed again, so no broken job keeps restarting at login. After upgrading aimux, run `gateway install` again too: `remote serve` and the worker are separate processes, and an older worker cannot list a source afresh for an approval from a client (it answers `503` saying to reinstall it).

Every sandbox turn's token is a lease: `aimux remote serve` puts it on the worker over `~/.aimux/gateway.sock` before the turn's claude starts, with the tools the turn may use and the tool snapshot it was compiled at, renews it every 2 minutes, and deletes it when the turn ends. A lease nobody renews expires after 15 minutes. The socket is mode 0600, the worker checks that every connection comes from your user, and it is never offered on a TCP port. A restarted worker knows no leases: `remote serve` asks the worker's status every 10 seconds during a turn and puts the turn's lease again once the restarted worker answers, and checks again every second while the worker does not answer or a renewal failed. For its first 15 seconds a started worker holds a call whose token it does not know yet (instead of answering 401, which makes Claude Code stop using that server for the turn) until the lease is put again; at most 64 calls wait, more get 503, and after the 15 seconds an unknown token gets 401 at once. The worker logs each lease put and delete by session (never the token) in `~/.aimux/logs/tool-gateway`, and, when it builds its servers, each backend that is down (with its error) and each one that serves no tools because none of its listed tools matches an approved pin (`aimux tools status` says why: `changed`, `unpinned`, `source_changed`, or not in any set). `aimux mcp proxy status` shows the worker on its `gateway` row.

The `openshell` commands the worker runs for `cli` and `http-openapi` sources get only `PATH`, `HOME`, `LANG`, `TMPDIR`, `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_STATE_HOME`, `OPENSHELL_GATEWAY`, `OPENSHELL_GATEWAY_INSECURE` and `OPENSHELL_LOCAL_TLS_DIR` from the worker's environment; every other variable stays out, `OPENSHELL_OIDC_CLIENT_SECRET` and cloud credentials included.

```bash
aimux mcp proxy status --json
```

The page is four tables, columns aligned in terminal cells with upper-case headers. `COMPONENT` is the proxy and the tool gateway: state, version, uptime, and the proxy's address or the gateway's leases and backends. The gateway reports no build version, so its VERSION is `-`; the tool-policy snapshot it serves is in its details as `snapshot sha256:…` (the first 12 digits). `SERVER` lists the servers that need you first: `failed`, a live server whose last error is newer than its last answered call and its last start (its state in yellow, a warning), and `no route` (a never-started server the proxy has no cached tools for). Then `running`, `starting` and `idle` (stopped after `--idle` without calls; it starts again on the next call and costs no memory meanwhile). Ready servers, never started but with an endpoint, are the normal resting state: the proxy answers a session's tool list from its catalog and starts a server only on its first tool call, so they are counted in the line under the table, with failed servers, warnings, no route, probe failures (a probe that failed on a server that keeps running) and removed entries. `--all` adds them as rows (`ready`), and removed ones too (`removed`, last: a moved server whose entry you removed from `~/.claude.json`, not drift, until `aimux mcp proxy install` takes it off the proxy). `ERRORS` holds each failed or warning server's message with its age (a `--probe` failure has none): a failure in red with the last stderr lines of a failed start, a recent error in yellow. An error the server has since recovered from (it answered a call, even with a tool's error or a JSON-RPC error, or started well afterwards, in the same session for a per-session server; a call that only came in, was cancelled, or finished on a backend a reload retired does not count) is past: it is left out, and `--all` shows it dim as `(old)`, never red. A `--probe` failure shows a removed server's row without `--all`. The last table has one row per thing to know: `WARNING` for what needs you (install state unknown, not installed, drifted entries, servers not behind the proxy yet, an upgrade restart pending, hooks off, servers with no route, a tool gateway that is not running or has backends down) and `INFO` for notes (how many servers are behind the proxy, hooks on, removed entries, servers kept direct with `--skip` or for a reason install recorded). `FIX` is the command to run, or empty; a fix with more than one step gets a row per later step, marked `then` (drifted entries: `aimux mcp proxy uninstall`, then `aimux mcp proxy install`; servers with no route: `aimux mcp proxy refresh`, then `aimux mcp proxy restart`). When the proxy answering is not the installed launchd job (no launchd agent, or another port than install recorded), `restart` cannot reach it, so the second no-route step reads `aimux mcp proxy serve`, labelled `then, again with your original flags`: start it again the way you started it. Install fixes carry `--port <n>` when the proxy was installed on another port than 7381, since install refuses a different port. Server names from your config in a command are passed one `--unskip` per name, each written as one field of the flag's comma-separated value (quoted when it holds a comma or a quote) and then quoted for the shell where it needs it. The page asks the tool gateway before it prints, so its row lines up with the proxy's; a gateway that does not answer delays the page by up to 5 seconds.

On a terminal the output is coloured (headers bold, green running, red failed, yellow warnings, `no route` and `WARNING`, dim idle, ready and `INFO`) and fits its width, measured in terminal cells (wide characters count twice): each table fits the terminal's width: its widest text column is cut with `…` rather than wrapping (`ADDRESS`, `SERVER`, or `MESSAGE` and then `SERVER` in `ERRORS`, so an error's age and message always show), each to 8 cells at least; when the columns still do not fit, the lines are cut at the width. A fix command is never cut: `MESSAGE` gives way, and when a command leaves it no room, the `FIX` column goes and each command is a line of its own under its message, whole, even past the width (a later step's `then` label is on the line before its command, so the command line pastes as it is). A server name cut to fit that would read the same as another keeps a short ending (`playwr…a` and `playwr…o`). Piped, with `NO_COLOR` set or with `TERM=dumb` it is plain text, and piped output is never cut or wrapped. `--all` changes the text page only. `--json` keeps the raw states (`not_started`, shown on the page as `ready` when the server has an endpoint and as `no route` when it has none; `starting`, `running`, `idle_stopped`, `failed`), unchanged for scripts, each server's `lastCall`, `lastOK` (when the server last answered a call; left out until it has) and `errorPast` (whether its last error is past: it answered or started well since, in the error's session for a per-session server; a call or start in another session leaves the warning; present whenever there is a last error, absent otherwise and from a proxy older than this field, whose errors the page takes as old unless one came after the server's last answer), `install.keptDirect` with each server once (the reason the Claude config gives now wins), the install state (with `removed`), and says per server whether the proxy has an endpoint for it (`endpoint`), and `hooks: true` when `~/.claude/settings.json` holds both server hooks. Error text and stderr have configured `env` values and token-shaped strings replaced by `[redacted]`. When the proxy is not running the command says so and exits 0 (`--json` prints `{"running":false}`, with the `install` state when it could be read). When it takes the connection but gives no status (an HTTP error, a timeout, a bad answer), the text page still prints what it knows of the install (the proxy row reads `no status`), without the tool gateway row, then the command fails with the reason; `--json` just fails. `--probe` waits up to `--timeout` (default 1 minute); a probe counts no tool calls, and a per-session server it starts is stopped again.

The daemon's part of this (servers, not the install state or the tool gateway) is at `GET http://127.0.0.1:7381/status` (and `POST /status/probe?timeout=30s`, which needs the header `X-Aimux-Probe: 1` so a web page cannot start your servers; add `&server=<name>` once per server to probe only those), local requests only.

`POST http://127.0.0.1:7381/reload` makes the running proxy re-read `~/.aimux/mcp-servers.json` and the catalog and apply the difference in place, without restarting: a new server gets its endpoint, a removed one loses it, and a changed one is served from its new definition (its running backend finishes in-flight calls first). It needs the same `X-Aimux-Probe: 1` header and answers `{"added": [...], "removed": [...], "changed": [...]}` with server names. `install` and `edit` call it for you. Those files are generated: change servers with `install` or `edit`, not by hand.

## Security

The proxy listens on `127.0.0.1` only, `/mcp/<server>` endpoints and `/status` alike. It rejects requests whose `Host` is not a loopback name (DNS rebinding) and requests a browser sends from another site.

## Failure handling

- A server that fails to start within 2 minutes returns an error result naming the server. Other servers keep working, and the next call tries again. Calls that arrive while a server is starting share that start; one caller giving up does not stop it for the others.
- A tool call may run up to Claude Code's default `MCP_TOOL_TIMEOUT` (100,000,000 ms, about 27.8 hours), the limit Claude Code puts on a direct call unless you change it. The proxy's limit is fixed: if you set a larger `MCP_TOOL_TIMEOUT`, calls through the proxy still stop at the default. A call that times out or loses its connection stops that server, and the next call starts a new one.
- A tool that reports an error keeps its server running.
- A server process that exits on its own is marked `failed` (`exited`) within about 10 seconds, also when it was a wrapper such as `npx` or `uv` whose child still holds its stderr open.
- A probe (`status --probe`, install's check) whose tool listing gets no answer returns at its deadline; until that listing returns, further probes of the server fail at once instead of queueing behind it, and if it has not returned after 2 minutes the server is stopped like a timed-out call. A probe that got no answer does not count as use, so the idle reaper still stops the server.
- `aimux mcp proxy refresh`, and `install` (with or without `--dry-run`) while it lists tools, interrupted with Ctrl-C or `SIGTERM` stop the servers they started (they run in sessions of their own, so the terminal's interrupt does not reach them), wait for them to close and say they were interrupted; an interrupted install changes nothing.
- A manifest from the earlier single-entry design is refused; restore `~/.claude.json` from `~/.aimux/backups` and, after moving `~/.aimux/mcp-proxy-install.json` aside, remove the agent with `aimux mcp proxy uninstall`.
- Claude Code does not end its MCP session when it exits. The proxy finds the process on the other end of each session's connection (one `lsof` per minute for sessions it does not know yet, trusting a port only while the connection that carried the session's request is still open, and the process by its pid and start time) and stops the session's per-session servers when that process exits, nightly `claude -p` runs included. Only a session whose process cannot be found falls back to `--idle`, and never while one of its calls is in flight. A long call never loses its session.

## Conformance check

`scripts/mcp-proxy-conformance.sh` runs the official MCP conformance suite (`@modelcontextprotocol/conformance@0.1.16`) against the reference server directly and through the proxy. The proxy run uses `scripts/mcp-proxy-conformance-baseline.yaml` to baseline known failures:

- **Tools only:** `logging-*`, `prompts-*`, `resources-*` scenarios (the proxy serves tools only, as above)
- **Unknown tool errors:** `tools-call-error`, `tools-call-simple-text` (the suite calls tools the reference server lacks; the reference server wraps that error in a tool result, while the proxy returns the JSON-RPC error `-32602` the specification defines for unknown tools)

The script exits 0 when all failures match the baseline, and exits non-zero on:
- **Unexpected failures** (new regressions)
- **Stale baseline entries** (a listed scenario now passes, so the baseline needs updating)

This runs on every relevant push: locally through pre-commit's `pre-push` stage (run `pre-commit install --hook-type pre-push` once per clone; the same stage also lints the pushed commits with `GOOS=linux`, and the other pre-commit hooks stay on commit), and in GitHub Actions when MCP proxy code changes.

## Live check

`scripts/mcp-proxy-live.sh` probes the owner's real MCP servers through the proxy. This runs only with explicit approval, and changes nothing:

- Reads `~/.claude.json` strictly read-only (copies it to a temp directory)
- Uses temporary `--servers` and `--catalog` paths, not the real `~/.aimux/` files
- Port 17462 (a different port from the installed proxy)
- Cleans up every process it starts on exit, including when it is cancelled during the refresh

It starts a throwaway proxy on port 17462 and runs `aimux mcp proxy status --probe` against it, so the proxy starts each stdio server once and lists its tools. It calls no tools. Output is one line per server, with error text taken from the proxy's status (already scrubbed of env values and tokens):

```
ok <name> <tool count>
failed <name> <first error line>
```

The script exits 0 even when servers fail (it is a report), and exits non-zero only if the proxy itself could not run.
