---
title: Parts and Their Settings
description: Say in one file which parts of aimux are on and how, and have aimux make the background services match.
---

aimux is made of parts: the sessions dashboard, the inference proxy, the MCP proxy, phone access, sandboxes. Some of them need a background service. The `parts:` section of `~/.aimux/config.yaml` says which parts you want on and how, and `aimux setup --apply` makes the services match. The services it manages today are the launchd jobs of the model proxy (the inference proxy part) and the MCP proxy; only the model proxy has settings beyond on and off.

Nothing here is required. With no `parts:` section, aimux manages no service and each one runs as it was installed.

## The section

```yaml
# ~/.aimux/config.yaml
parts:
  inference-proxy:
    enabled: true
    port: 7385
    serves: [messages]
    engines:
      codex:
        service_tier: priority
      anthropic:
        enabled: true
      enmaas:
        type: messages
        url: https://gateway.example
        key: {keychain: {item: enmaas-key}}
        enabled: true
  mcp-proxy:
    enabled: true
```

The inference proxy has two sides. `serves` is the front: the APIs a client may speak to it, which today is the Messages API, since the client is Claude Code. `engines` is the back: who answers. Each engine has a name, which is what you type before the colon of a model name (`enmaas:claude-opus-5-5`).

| Key | Under | Meaning | When left out |
|---|---|---|---|
| `enabled` | a part | `true`: aimux manages its service: it takes the job as it is, changes its arguments when the settings ask, and starts it when it does not run. `false`: for the inference proxy, aimux stops its service and keeps it stopped, through a crash and the next login, until it is turned on again; the MCP proxy is left running and you are pointed at `aimux mcp proxy uninstall`, which also gives Claude Code its servers back | Not allowed. A part that is listed says one or the other |
| `port` | `inference-proxy` | The port on 127.0.0.1 | What the installed job has |
| `serves` | `inference-proxy` | The APIs a client may speak; `messages` is the only one this build knows | `[messages]` |
| `engines` | `inference-proxy` | The engines, by name | What the installed job has |
| `models` | `inference-proxy` | Names for models, the one place a model name is written: `implement: codex:gpt-6.2-sol`. A value is a model as a session would name it, or `codex:default` for the proxy's current default Codex model. Its engine has to be on in this file | No entries |
| `roles` | `inference-proxy` | Which entry of `models` a kind of work uses. The one role is `subagent`: your own subagents that name no model. A role names an entry, never a model, so a new model is one changed line. The main conversation is chosen in the session, and a kind of subagent that should differ names its model in its own definition | No role: every kind of work uses the session's model |
| `on_limit` | `inference-proxy` | What the proxy does when a plan limit comes back. `report` is the one value in this build: on the failed call's ledger line it records what a fallback would have done (`would:codex`, or `would_not:` with the reason) and changes nothing; the session gets the provider's own answer | What the installed job has; nothing is reported for a job without it |
| `type` | an engine | The protocol the proxy speaks to it: `codex-app-server` or `messages` | Implied for `codex` and `anthropic`; required for any other name |
| `auth` | a `messages` engine | Whose credential is sent: `caller` (the session's own login), which only `anthropic` may use, or `key` (your key for that engine), which is the only one an engine you name may use | `caller` for `anthropic`, `key` for any other |
| `url` | a `messages` engine | Where it is; `https` unless on this machine | Required for an engine you name. `anthropic` always goes to `https://api.anthropic.com` and cannot be given another |
| `key` | a `messages` engine with `auth: key` | Where its key is kept: `{keychain: {item: ...}}`, `{env: {name: ...}}`, `{file: {path: ...}}` or `{cmd: {argv: [...]}}`. Never the key | `{keychain: {item: <name>-key}}` |
| `enabled` | an engine | Requests naming it are answered | On, for an engine that is listed. `codex` cannot be turned off |
| `service_tier`, `binary` | `codex` | The tier (`priority` or `standard`) and the Codex program to run | What the installed job has |

`models` and `roles` reach a session through its shell: `aimux model proxy env` sets Claude Code's own variable for the model subagents use by default, so they hold for sessions started after that and not for one already running. `on_limit: report` becomes `--on-limit report` in the proxy's start command at the next `aimux setup --apply`, which restarts the proxy after asking.

Three rules are worth knowing before you edit it:

- **A part has three states.** Not listed: aimux neither starts nor stops it. `enabled: true`: aimux manages it. `enabled: false`: aimux stops the inference proxy and keeps it stopped; for the MCP proxy it stops nothing and names `aimux mcp proxy uninstall`. Adding one part to the file never touches another.
- **A setting left out means "as it is installed".** `inference-proxy: {enabled: true}` on a proxy that runs with a port you chose keeps that port. A setting you write replaces the installed one. Engines are stated together: once the file lists engines, they replace the ones the job had, and `engines:` with nothing under it means none besides Codex.
- **No secret goes in the file.** A key is a reference to where it is kept.

## Change it with a command

You can edit the file yourself, let a command change one thing in it, or pick parts from the list `aimux setup` opens with on a terminal, which does what `aimux enable <part>` does for each number you type. A command leaves the rest of the file as you wrote it: your comments, your order, your spacing.

```bash
aimux engine list                       # what the file states, and what the running proxy answers with
aimux engine enable anthropic           # switch on an engine that exists
aimux engine disable anthropic          # switch it off; its settings stay
aimux engine add enmaas=https://gateway.example    # a new address that speaks the Messages API
aimux engine remove enmaas              # forget it
aimux enable mcp-proxy                  # a part
aimux disable mcp-proxy
```

Two verbs for two things. `enable` and `disable` switch something that exists, and keep its settings, so a gateway turned off for a day comes back without retyping its address. `add` and `remove` are for an engine of your own, which needs a name and an address. Anthropic and Codex are built in: Anthropic is switched on, not added, and Codex is always on.

Each command that changes something (all of these but `list`) changes the file, shows what that means for the services, and makes them match, asking before a restart. `--yes` agrees in advance, and `--no-apply` only changes the file, for `aimux setup --apply` to pick up later. If you answer no to the restart, or there is nobody to ask and no `--yes`, the file keeps the change and the service keeps running as it was; the command says so, exits 1, and names `aimux setup --apply` as what applies it. With `--no-apply --json` it prints `{"schema_version": 1, "changed": ..., "applied": false}`.

`aimux disable inference-proxy` stops the model proxy, after asking, and tells launchd to keep it off; sessions that go through it get no answer until `aimux enable inference-proxy` starts it again from the same job file, which is not changed. The MCP proxy is more than a job, since Claude Code's server entries point at it, so it is turned off with its own command, `aimux mcp proxy uninstall`, which gives Claude Code its servers back; `aimux disable mcp-proxy` says so and exits 1.

A command about one part or one engine applies only that part: what the file says about another part waits for `aimux setup --apply`, so a stop you staged with `--no-apply` or answered no to is never carried out as a side effect of something else. A proxy that is turned off is skipped by `aimux upgrade`, which says so and still upgrades the others; it is upgraded once it is on again, and naming it on the command line while it is off exits 1. A proxy started by hand, with no job, is not aimux's to stop: the command says it still answers.

A command never reports success when the file was changed and the machine could not follow: a proxy started by hand, a job file aimux cannot edit, or a part aimux starts and stops nothing for yet (phone access, sandboxes). It says which and exits 1.

`aimux engine add` expects the engine's key in the secret-store entry `<name>-key`, and writes that reference into the file. When the entry is not there yet, it says so and how to create it. It never reads the key.

`aimux engine list` reads the file and asks the running proxy; it changes nothing. It shows both sides, so a difference is visible:

```text
ENGINE     IN THE FILE  RUNNING  TYPE              WHERE                                          KEY
codex      on           yes      codex-app-server  the Codex program, on your ChatGPT plan
anthropic  on           no       messages          https://api.anthropic.com (your Claude login)
enmaas     off          no       messages          https://gateway.example                        secret store: enmaas-key

The running proxy and the file differ. To make them match: aimux setup --apply
```

When the file says nothing about engines, the column reads `not stated` and nothing is reported as differing: the proxy runs with what it was installed with. A proxy from before it listed its engines shows `-` under `RUNNING`. With `--json` it prints `{"schema_version": 1, "port": ..., "engines": [...]}`, each engine with `name`, `on`, `stated` and `type`, and where they apply `auth`, `url` and `key_at` (Codex has none of the three), and `running` when the proxy says.

Stating an engine takes the inference proxy under management: the file gains `inference-proxy: enabled: true` if it was not listed. Once the file lists engines, they are the proxy's engines: one the job was started with by hand and the file does not list is dropped at the next apply, which the table shows before anything restarts.

## See what would change

```bash
aimux setup --check
```

It reads the section, compares it with each service's job, and prints what `--apply` would do. It changes nothing. It exits 1 when something would change, so a script can test it, and it lists every problem in the section with its line when the section cannot be used.

With `--json` it prints `{"schema_version": 1, "stated": ..., "changes": ..., "plan": [...]}`, each line of the plan with `part`, `service`, `action` (`none`, `adopt`, `change arguments`, `start`, `stop`, `skip`), the arguments `was` and `now`, `restarts` and a `note`. A section with problems gives `{"schema_version": 1, "problems": [...]}`, and `--apply --json` gives `{"schema_version": 1, "results": [...]}`, each result a plan line with its `outcome` (`unchanged`, `adopted`, `changed`, `started`, `stopped`, `rolled back`, `failed`, `skipped`) and a `detail`.

```text
PART             SERVICE      WILL        DETAIL
inference-proxy  model proxy  restart     from: model proxy serve
                                          to:   model proxy serve --anthropic
mcp-proxy        mcp proxy    be managed  as it runs now; no restart
```

## Make the services match

```bash
aimux setup --apply
```

It shows the same table, asks before it restarts a service (`--yes` agrees in advance; with nobody to ask and no `--yes` it refuses), and then does exactly what the table said.

What it will and will not touch in a job file:

- It changes only the arguments that come from the settings: the port, the Codex tier and program, and the engines. The job's environment, its log paths, when it restarts, and any other argument you added by hand stay as they are. An argument of that list which you set by hand is kept until the file states that setting; then the file wins.
- Taking a service under management costs nothing: when its job already runs what the settings state, the file is not rewritten and the service is not restarted.
- The job file as it was before aimux first managed it is kept in `~/.aimux/services/<service>/job.before-aimux.plist`.
- A service that runs an older build than the `aimux` you typed is not given new arguments: it may not know them. The table says so and names `aimux upgrade <service>`, which comes first.
- A job file it cannot read safely is left alone, with the reason: one with a separate `Program` key, a comment, or arguments after a bare `--`.

`--apply` exits 1 when a service the settings are about was left alone, as it does when a restart failed: the machine does not match the file, and the output says why. `--check` in the same case exits 0, since nothing would change.

If a service does not answer after its restart, its old job file is written back and it is started from that again. The command says so and exits 1. That holds when you interrupt it while it waits: the wait ends, and the job file still goes back before the command returns. The service is asked on the port its new arguments give it, so changing the port is not mistaken for a service that did not come up.

A service of a part that is on, whose job is right and which does not answer, is started. A part that is off and whose port still answers after its job was stopped is reported, not called off: something else was started on that port.

Moving the model proxy to another port moves `aimux status` and `aimux upgrade` with it: both read the port from the job. A session still has to be pointed at the new port (`aimux model proxy env --port`), and the proxy's request history and ledger are kept per port, so a new port starts new files.

Making a job for a service that has none is not built yet: `--check` says so for that part and `--apply` leaves it as it is.

## Models and roles

A role says which model a kind of work uses. So that a new model is one changed line, a role never names a model: it names an entry under `models`.

```bash
aimux engine model update implement codex:gpt-6.2-sol   # name a model
aimux engine role update subagent implement             # your own subagents that name no model use it
aimux engine list                                       # what each role and each subagent runs on
aimux engine role delete subagent                       # back to the session's model
aimux engine model delete implement                     # refused while a role still uses it
```

`aimux engine list` then shows, under the engines:

```text
ROLE      MODEL                          ENGINE
main      (the session's)                -
subagent  implement = codex:gpt-6.2-sol  codex

SUBAGENT       DEFINED IN        ITS MODEL            RUNS ON
reviewer       ~/.claude/agents  codex:gpt-6.2-astra  codex
helper         ~/.claude/agents  (none: the role's)   codex
```

The second table is your own subagent definitions, from `~/.claude/agents` and the project's `.claude/agents`. One that names a model in its definition (`model:` in its front matter) keeps it: Claude Code lets that win over any default, so that is where a kind of subagent that should differ says so. aimux reads those files and never edits them. Built-in subagents and those a plugin brings are not listed; the built-in Explore uses the session's model whatever the role says.

There is one role, `subagent`. The main conversation's model is chosen in the session, with `/model`. These commands change the file only: no service runs differently for a role.

A role reaches a session through its shell. `aimux model proxy env` reads the role from the file and sets `CLAUDE_CODE_SUBAGENT_MODEL`, the variable Claude Code reads when it starts for the model its subagents use by default. So:

- It holds for sessions started from a shell set after the change. A session that is already running keeps what it started with; exit and resume it to pick up a new role.
- `AIMUX_ROLES=off` in a shell's environment leaves the role out for that shell.
- A value of your own in that variable is left alone, and `aimux model proxy env` says so.
- A role whose engine the running proxy does not answer with is not set, and it says which engine.
- `aimux model proxy env --off` takes the variable back, and only when aimux set it.

## Switch engine inside a session

After `eval "$(aimux model proxy env)"`, sessions started from that shell list a Codex model in `/model`, next to the Claude ones, so switching engine is a choice from the list:

```text
9. Codex gpt-6.2-sol     aimux proxy, on your ChatGPT plan
```

Any other model the proxy answers is chosen by name: `/model codex:gpt-6.2-astra`, or `/model <upstream>:<model>` for a named upstream. `/model` and a Claude model goes back. Claude Code reads the entry when it starts, so a session that was already running needs `claude --resume` from the shell to show it. Claude Code has room for one such entry: when the shell already has one of its own (`ANTHROPIC_CUSTOM_MODEL_OPTION`), aimux leaves it and says to switch by name. `aimux model proxy env --off` removes the entry again, and only when it is aimux's.

## See where a shell's sessions go

A session goes through the model proxy only when the shell that started it points at the proxy (`aimux model proxy env`); every other session goes straight to Anthropic, or to whatever other gateway or provider its shell names, and is not recorded. To see which it is, and whether the proxy answers:

```bash
aimux model proxy route --model codex:gpt-6.2-sol
```

It prints one line, made for a status line or a prompt:

```text
direct · anthropic claude-opus-5-5
proxy :7385 ok · codex gpt-6.2-sol
proxy :7385 DOWN · codex gpt-6.2-sol
proxy :7385 ok · anthropic claude-opus-5-5 (the anthropic engine is off)
another gateway
```

`--model` is the model the session is on now, as Claude Code names it, so the line follows `/model`; without it the model the shell pins is used, if it pins one. The command reads the shell's environment and the proxy's keyless health answer, waits half a second at most, and never prints the proxy key or sends it anywhere.

With `--json` it prints `{"schema_version": 1, "through_proxy", "port", "mode", "engine", "model", "proxy": {"state", "build", "engines", "engine_on"}}`. `mode` is `direct`, `engines` or `codex` (the two forms `env` sets), `unmarked` (a proxy on this machine, set by hand) or `elsewhere` (another gateway). `proxy.state` is `ok`, `degraded`, `down` (nothing answers on the port) or `not aimux` (something else answers there); `proxy` is left out when the sessions do not go through a proxy.

It exits 1 when the sessions go through a proxy that does not answer, or whose engine for that model is off, so a status line can turn red on the exit code alone.

## When the proxy misbehaves

One command checks the things that break in practice and names the fix for each:

```bash
aimux model proxy doctor            # the everyday proxy
aimux model proxy doctor --port 7386
```

```text
Model proxy on 127.0.0.1:7385. 1 thing to look at; nothing is failing.

CHECK    STATE  DETAIL
service  ok     answers on 127.0.0.1:7385
build    warn   its build 283 is older than the CLI (289), so it lacks what was fixed since
key      ok     the proxy holds the stored key
codex    ok     the Codex login works, checked 1m ago
ledger   ok     every call is recorded
engines  ok     answers with codex
calls    ok     30 calls in the last hour, none failed
shell    ok     sessions started from this shell do not go through the proxy, so it does not see them

FIX
  build: aimux upgrade model-proxy
```

| Check | What it looks at | When it is not ok |
|---|---|---|
| `service` | Whether something answers on the port, and whether it is the model proxy | `fail`: nothing answers, or something else listens there. `warn`: the proxy says it is degraded, with its reason |
| `build` | The proxy's build against this aimux | `warn`: it is older; `aimux upgrade model-proxy` |
| `key` | Whether a proxy key is stored, and whether the listener proved it holds the same one | `fail`: no key yet, or a listener that does not hold it |
| `codex` | The proxy's own check of the Codex login, which costs no tokens | `fail`: the last check failed, with its words. `warn`: the last good one is more than 15 minutes old |
| `ledger` | Whether calls are being recorded | `fail`: the ledger could not be opened. `warn`: some lines were lost |
| `engines` | The engines it answers with against the ones the config file states | `warn`: they differ; `aimux setup --apply` |
| `calls` | The last hour of requests, from the proxy's request history | `warn`: a rate limit (the plan's, not the proxy's) or an upstream's own failure. `fail`: a refused login, or calls that failed before any answer |
| `shell` | Whether the shell you ran it in points at this proxy, and at an engine it has | `fail`: the engine is off; `aimux engine enable <name>` |

The `FIX` section lists a command only for the checks that have one; a rate limit, for instance, has none, and in `--json` such a finding has no `fix`. It reads only: nothing is started, restarted or changed, and no tokens are spent. The proxy key is sent only to a listener that first proved it holds the same key, and only down the connection that proof came back on. When nothing answers, the checks that need an answer are left out instead of guessed. It exits 1 when something is failing; a warning alone exits 0. With `--json` it prints `{"schema_version": 1, "port", "verdict", "findings": [{"id", "level", "detail", "fix"}]}`, `verdict` being the worst level.

## The same answers for the dashboard

The dashboard's server gives three of these reports as JSON, from the functions the commands print from, so a page and a terminal cannot disagree. Each reads only.

| Address | The command it matches | What it answers with |
|---|---|---|
| `GET /api/services` | `aimux status --json` | The same document: `cli_build`, `services` (each with its `state`, `build` and `address`) and `attention`, what is wrong with the command that fixes it |
| `GET /api/proxy/doctor` | `aimux model proxy doctor --json` | The same document (`port`, `verdict`, `findings`, each with a `level`, a `detail` and, where a command fixes it, a `fix`) with one difference: the finding about the shell is left out, since a page is not in one, so the `verdict` is the worst of the others |
| `GET /api/engines` | `aimux engine list --json` | The same document: `engines`, `roles` and `subagents`. The subagent definitions are those of your home folder and of the folder the dashboard was started in |

When one of them cannot be read (a config file with a problem, a secret store that is locked), the answer is a 500 with an `error` saying why. No page of the dashboard shows them yet.
